## 결제의 등장인물: PG · 가맹점 · 카드사 · 결제수단 · MID · API 키

**상황**
- 쇼핑몰에 카드 결제를 붙이려는데, 신한·국민·삼성·현대 같은 **카드사마다 따로 계약하고 따로 연동**해야 한다면 몇 달이 걸린다.
- 고객은 카드 말고도 **카카오페이·네이버페이·토스페이, 계좌이체, 가상계좌, 휴대폰 결제**까지 원한다.
- AI에게 "결제 붙여줘"라고만 했더니, 어느 회사와 어떤 방식으로 연동할지 몰라 엉뚱한 예제 코드가 나왔다.
- 결제 연동 예제에 있던 **비밀 키**를 프런트엔드 코드에 그대로 넣었다.

**용어**
- **merchant(가맹점, 상점)** — 카드 결제를 **받는 쪽**, 즉 내 쇼핑몰. 카드사와 "우리 가게에서 이 카드를 받겠다"는 계약을 맺은 곳.
- **카드사(card issuer, 카드 발급사)** — 고객에게 카드를 내준 회사. 결제를 **허락할지**(한도·도난 여부) 판단하고, 나중에 고객에게 **청구**한다.
- **PG(Payment Gateway, 결제대행사)** — 쇼핑몰과 카드사·은행·간편결제사 **사이에서 결제를 대신 처리**해 주는 회사(진단 Q2). 토스페이먼츠, KG이니시스, 나이스페이 등.
  - **왜 거치나** — PG가 여러 카드사와 미리 계약된 **대표 가맹점** 역할을 하고, 내 쇼핑몰은 PG 아래의 **하위 가맹점**으로 들어간다. 카드사마다 계약·심사·연동할 필요 없이 **PG 한 곳과 계약 + 연동 한 번**으로 카드·간편결제·계좌이체·가상계좌를 모두 받는다.
  - **대가** — 결제 금액의 일정 비율을 **PG 수수료**로 떼고, 돈을 바로 주지 않고 며칠 뒤 모아서 **정산**해 준다(다음 레슨).
  - 비유: **택배 대행사**. 쇼핑몰이 CJ·한진·롯데와 각각 계약하는 대신 대행사 한 곳에 맡기면 알아서 보내 주는 것과 같다. 대신 수수료를 낸다.
- **payment method(결제수단)** — 카드, **간편결제**(카카오페이·네이버페이·토스페이처럼 카드·계좌를 미리 등록해 두고 비밀번호·생체 인증으로 결제), 계좌이체, **가상계좌**(주문마다 발급되는 임시 입금 계좌, 무통장입금), 휴대폰 결제. PG 하나로 대부분을 묶어서 쓴다.
- **결제창(결제위젯)** — PG가 제공하는 **결제 화면**. 카드번호 입력·카드사 인증이 PG 화면 안에서 이뤄져서, 내 서버는 **카드번호를 만지지 않는다**. 카드번호를 직접 받아 저장하면 보안 의무가 크게 늘어나므로 결제창을 쓰는 게 기본.
- **MID(Merchant ID, 상점 아이디)** — PG가 내 가맹점에 붙여 주는 **식별 번호**. PG 관리자 화면·정산 내역·문의할 때 쓰인다.
- **API 키 두 종류** — 대부분의 PG가 나눠서 준다.
  - **client key(클라이언트 키)** — 브라우저에서 결제창을 띄울 때 쓰는 **공개해도 되는 키**.
  - **secret key(시크릿 키)** — 서버에서 결제를 **확정·취소**할 때 쓰는 비밀 키. **프런트엔드에 넣으면 누구나 내 가게 이름으로 결제를 취소할 수 있다**(상황 4, 웹·앱 보안 용어의 비밀 관리와 같은 원칙). 반드시 서버 환경 변수에.
  - **test key / live key** — 실제 돈이 오가지 않는 **테스트 키**로 먼저 개발하고, 가맹점 심사 통과 후 **라이브 키**로 바꾼다.

**지시 예문**
- "토스페이먼츠 결제위젯으로 카드·간편결제를 붙여줘. 결제창은 PG 화면을 쓰고, 우리 서버는 카드번호를 받거나 저장하지 않게 해줘."
- "PG 클라이언트 키는 프런트엔드에, 시크릿 키는 서버 환경 변수에만 두고, 시크릿 키가 클라이언트 번들에 섞이지 않았는지 확인해줘."
- "지금은 테스트 키로 개발하고, 라이브 키로 바꿀 때 바꿔야 할 설정 목록을 정리해줘."

## 돈이 움직이는 순서: 인증 · 승인 · 매입 · 정산 · 매입 전 취소

**상황**
- 고객이 결제 버튼을 눌렀는데, 돈이 판매자 통장에 들어오기까지 무슨 일이 일어나는지 모른다(진단 Q1).
- 고객 카드 앱에는 "승인" 문자가 왔는데, 내 통장에는 며칠째 돈이 안 들어온다.
- 같은 "결제 취소"인데 어떤 건 고객 카드에서 바로 사라지고, 어떤 건 환불까지 며칠이 걸린다.
- 결제 연동 문서에 "결제 요청 → 인증 → 승인"이라고 적혀 있어서 인증과 승인을 같은 말로 알았다.

**용어**
- 전체 흐름: **요청 → 인증 → 승인 → 매입 → 정산**. 앞의 셋은 결제 버튼을 누른 그 순간 몇 초 안에, 뒤의 둘은 며칠에 걸쳐 일어난다.
- **결제 요청** — 쇼핑몰이 PG에 "이 주문, 이 금액으로 결제창 띄워 줘"라고 보내는 것.
- **authentication(인증)** — 결제창에서 고객이 **본인임을 확인**하는 단계(카드 앱·비밀번호·생체 인증). 아직 돈은 확정되지 않았다. PG가 쇼핑몰로 "인증 성공" 결과를 돌려준다.
- **authorization(승인)** — 쇼핑몰 서버가 PG에 **승인 요청**을 보내고, 카드사가 "이 카드로 이 금액 결제 가능"(한도·정지 여부)을 확정하는 단계. 이때 고객 카드에 **"승인" 문자**가 온다(상황 2). 인증과 승인은 다른 단계라서, **인증만 되고 승인을 안 보내면 결제가 완료되지 않는다**(상황 4).
- **매입(capture, 매출 확정)** — PG가 승인된 거래 데이터를 모아 **카드사에 넘겨 실제 대금 청구를 시작**하는 단계. 보통 결제 다음 영업일에 자동으로 처리된다. 이때부터 매출이 확정된다.
  - **매입사(acquirer)** — 가맹점을 대신해 카드 대금을 사들이는 쪽. 고객 카드를 발급한 **발급사(issuer, 1번 레슨 카드사)**와 짝이 되는 말.
- **정산(settlement)** — 매입된 금액에서 **PG 수수료를 뗀 돈**이 가맹점 통장에 들어오는 단계. 결제 당일이 아니라 **며칠 뒤**(PG·계약·업종마다 주기가 다름)라서 "승인됐는데 돈이 없다"(상황 2)가 정상이다. 이 주기를 **D+N**(결제일 Day 기준 N영업일 뒤)으로 부른다.
- **취소 시점에 따른 차이**(상황 3)
  - **매입 전 취소(승인 취소)** — 매입되기 전, 보통 **결제 당일**에 취소. 카드사로 청구가 넘어가기 전이라 **바로 사라진다**.
  - **매입 후 취소** — 이미 매출이 확정된 뒤라 카드사가 다시 **취소 매입** 절차를 밟아야 해서, 고객 카드에 반영되기까지 **며칠 걸린다**.
  - 고객 문의 "취소했는데 왜 아직 안 빠졌죠?"의 대부분이 이 차이다.
- 비유: **식당 외상 장부**. 승인은 주인이 "이 손님 외상 돼요" 확인하는 것, 매입은 장부를 정리해 **본사에 청구서를 넘기는 것**, 정산은 본사가 수수료를 떼고 **돈을 보내 주는 것**. 청구서 넘기기 전에 지우면(매입 전 취소) 깔끔하지만, 넘긴 뒤에는 정정 서류(취소 매입)가 다시 오가야 한다.

**지시 예문**
- "결제 흐름을 요청 → 인증 → 승인 순서로 구현해줘. 결제창 인증 성공 후 우리 서버에서 PG 승인 API를 호출해야 주문을 '결제 완료'로 바꿔줘."
- "주문 관리 화면에 결제 상태(승인·매입·취소)와 정산 예정일을 함께 보여줘."
- "고객이 결제를 취소하면 매입 전/후에 따라 '즉시 취소' 또는 '카드사 반영까지 영업일 기준 며칠 소요' 안내 문구를 다르게 보여줘."
