## Layout shift와 CLS

**현상** — 글을 읽는데 위쪽 이미지·광고가 늦게 뜨면서 본문이 갑자기 아래로 밀린다. 버튼을 누르려는 순간 버튼이 밀려 엉뚱한 걸 누르게 된다.

**용어**
- **layout shift** — 이미 화면에 보이던 요소가 예고 없이 위치를 옮기는 현상 하나하나.
- **CLS (Cumulative Layout Shift)** — 페이지가 살아 있는 동안 생긴 layout shift를 점수로 매긴 지표. Core Web Vitals 세 지표 중 하나. **0.1 이하**면 "좋음"이다.
- 클릭·키 입력 직후(0.5초 이내)에 생긴 이동은 사용자가 예상한 변화로 보고 CLS에 넣지 않는다. 아코디언을 눌러 펼친 것은 layout shift로 치지 않는다.

**원인** — 공통점은 **자리를 미리 잡아두지 않은 요소가 나중에 끼어드는 것**이다. 식당에서 일행 자리를 안 맡아두면 늦게 온 사람이 끼어 앉을 때 모두가 한 칸씩 밀려나는 것과 같다.
- `width`/`height`(또는 `aspect-ratio`)를 지정하지 않은 이미지·영상·iframe
- 늦게 삽입되는 배너·광고·쿠키 안내
- 웹폰트가 늦게 로드돼 글자 폭이 바뀌면서 줄바꿈이 달라짐

**지시 예문**
- "히어로 이미지에 width/height를 지정해서 로드 전에 공간을 예약하고, CLS를 없애줘."
- "상단 공지 배너가 늦게 들어와 본문을 밀어내. 배너 자리를 min-height로 미리 잡아줘."
- "웹폰트 교체 때 layout shift가 생겨. 폴백 폰트 크기를 맞춰서 줄바꿈이 안 바뀌게 해줘."

## LCP

**현상** — 페이지에 들어가면 헤더·메뉴는 금방 뜨는데, 정작 화면 한가운데 큰 대표 이미지(또는 큰 제목)가 한참 뒤에 나타난다. "페이지가 느리다"는 체감의 대부분이 이것이다.

**용어**
- **LCP (Largest Contentful Paint)** — 첫 화면(viewport) 안에서 **가장 큰 이미지나 텍스트 덩어리**가 그려진 시점. 페이지 로드 시작부터 잰다. Core Web Vitals 세 지표 중 하나이며 **2.5초 이하**면 "좋음"이다.
- 후보: `<img>`, 영상 poster, CSS `background-image`, 큰 텍스트 블록(제목·문단). 대개 히어로 이미지가 LCP 요소가 된다.
- 식당에 비유하면 반찬이 먼저 깔리는 건 상관없고, **메인 요리가 나온 시각**을 재는 것이다.

**원인**
- 서버 응답 자체가 느림 (HTML이 늦게 옴)
- 렌더링을 막는 CSS·JS가 먼저 다 받아져야 그림을 그리기 시작함
- 히어로 이미지가 너무 무겁거나(원본 PNG 등) 늦게 발견됨
- 히어로 이미지에 `loading="lazy"`를 걸어 오히려 늦게 받음 — 흔한 실수
- 클라이언트 렌더링(CSR)이라 JS 실행이 끝나야 본문이 생김

**지시 예문**
- "히어로 이미지가 LCP 요소야. lazy loading 빼고 `fetchpriority="high"`로 우선 로드해줘."
- "LCP 이미지를 WebP/AVIF로 바꾸고 화면 크기에 맞는 사이즈만 받게 해줘."
- "LCP가 3초 넘게 나와. 원인이 서버 응답인지, 이미지인지, 렌더 블로킹 리소스인지 먼저 분석해줘."

## INP

**현상** — 버튼을 눌렀는데 0.5초쯤 아무 반응이 없다가 뒤늦게 바뀐다. 입력창에 타이핑하면 글자가 한 박자 늦게 찍힌다. 그래서 같은 버튼을 두세 번 누르게 된다.

**용어**
- **INP (Interaction to Next Paint)** — 클릭·탭·키 입력 후 **화면에 다음 변화가 그려지기까지 걸린 시간**. 스크롤·hover는 재지 않는다. 페이지에서 일어난 상호작용 중 거의 가장 느린 것을 대표값으로 쓴다. Core Web Vitals 세 지표 중 하나이며 **200ms 이하**면 "좋음", 500ms 초과면 "나쁨"이다. 2024년 3월에 FID를 대체했다.
- **main thread** — 브라우저가 JS 실행, 레이아웃 계산, 화면 그리기를 **한 줄로** 처리하는 작업 통로. 은행 창구 직원이 한 명뿐인 것과 같다. 앞 손님 업무가 길면 뒤 손님(클릭)은 기다린다.
- **long task** — main thread를 50ms 넘게 붙잡는 작업. INP를 망치는 주범.

**원인**
- 클릭 핸들러 안에서 무거운 계산·대량 데이터 정렬을 바로 실행
- 상태 하나 바꿨는데 화면 전체가 다시 렌더링됨
- 수천 개 행을 한 번에 DOM에 그리는 긴 목록
- 광고·분석 같은 서드파티 스크립트가 main thread를 점유

**지시 예문**
- "필터 버튼 누르면 반응이 늦어. 버튼 상태부터 즉시 바꾸고 무거운 필터링은 그다음에 처리해서 INP를 줄여줘."
- "검색 입력할 때마다 목록 전체가 다시 렌더링돼. 입력은 debounce하고 목록은 virtualization 적용해줘."
- "INP가 나빠. Performance 패널 기준으로 long task를 찾아서 쪼개줘."

## Stacking context

**현상** — 모달·드롭다운에 `z-index: 9999`를 줬는데도 헤더나 다른 카드 아래에 깔린다. 숫자를 더 키워도 그대로다.

**용어**
- **stacking context(쌓임 맥락)** — z-index 순서를 따지는 **독립된 층 묶음**. z-index는 같은 묶음 안에서만 비교된다. 묶음 안의 자식이 9999여도, 묶음 자체가 다른 묶음보다 아래면 통째로 아래에 깔린다.
- 비유: 스테이플러로 찍은 종이 묶음. 묶음 안에서 종이 순서는 마음대로 바꿀 수 있지만, 묶음 안의 한 장만 빼서 다른 묶음 위로 올릴 수는 없다.
- **새 묶음을 만드는 속성** (부모에 이게 있으면 의심):
  - `position: relative/absolute` + `z-index` 값 지정
  - `position: fixed/sticky`
  - `transform`, `filter`, `opacity` 1 미만, `will-change`
  - flex/grid 자식에 `z-index` 지정
  - `isolation: isolate` (묶음을 일부러 만들 때 쓰는 속성)

**원인** — 애니메이션용 `transform`, 페이드용 `opacity` 같은 **겉보기와 무관한 속성**이 부모에 걸려 몰래 새 묶음이 생김. 그래서 z-index만 보고는 원인을 못 찾는다.

**지시 예문**
- "모달이 헤더 아래 깔려. z-index 올리지 말고, 부모 중 stacking context를 만드는 요소부터 찾아줘."
- "모달을 portal로 body 바로 아래에 렌더링해서 부모 stacking context에서 빼줘."
- "z-index 값이 여기저기 9999로 난무해. 레이어 순서를 토큰으로 정리해줘 (dropdown < sticky header < modal < toast)."

## Race condition

**현상** — 검색어를 "react" → "redux"로 빠르게 바꿨는데, 화면에 "react" 결과가 남는다. 탭을 빠르게 A → B로 눌렀는데 A 탭 데이터가 B 탭에 뜬다. 가끔만 생기고 재현이 잘 안 된다.

**용어**
- **race condition(경쟁 상태)** — 여러 작업이 동시에 진행될 때, **끝나는 순서**에 따라 결과가 달라지는 버그. 웹에서는 "먼저 보낸 요청이 늦게 도착해 최신 결과를 덮어쓰는" 형태가 가장 흔하다.
- 비유: 배달 앱에서 주소를 A → B로 바꿨는데, 서버에 "A로 변경" 처리가 늦게 끝나 최종 주소가 A로 남는 것. 보낸 순서 ≠ 도착 순서.
- **stale response** — 이미 쓸모없어진(낡은) 요청의 응답. race condition을 막는 핵심은 이걸 버리는 것이다.
- 네트워크가 빠른 개발 환경에선 잘 안 보이고, 느린 모바일 환경에서 터진다. 그래서 "가끔 이상해요"라는 제보로 들어온다.

**원인** — 요청을 보낼 때마다 응답이 오면 **무조건 화면에 반영**하도록 짜서, 응답이 오는 순서를 보장하지 않음.

**해결 방향**
- 새 요청을 보낼 때 이전 요청을 **취소** (`AbortController`)
- 응답이 와도 **최신 요청의 응답인지 확인**하고 아니면 무시
- 데이터 패칭 라이브러리(TanStack Query, SWR)는 이 처리를 기본으로 해준다

**지시 예문**
- "검색어를 빠르게 바꾸면 이전 결과가 남아. race condition 같으니, 새 요청 보낼 때 이전 요청은 AbortController로 취소해줘."
- "탭 전환 시 stale response가 화면을 덮어써. 현재 탭과 다른 응답은 무시하게 해줘."
- "개발자 도구에서 네트워크를 Slow 4G로 두고 race condition 재현되는지 확인해줘."

## Hydration과 hydration mismatch

**현상** — 새로고침 직후 콘솔에 "Hydration failed" / "Text content does not match" 경고가 뜨고, 처음 보인 텍스트가 잠깐 뒤 다른 값으로 바뀐다. 심하면 그 영역이 통째로 다시 그려지며 깜빡인다.

**용어**
- **SSR (Server-Side Rendering)** — 서버가 HTML을 완성해서 보냄. 빨리 보이지만, 이 상태의 HTML은 버튼을 눌러도 반응하지 않는 "그림"이다.
- **CSR (Client-Side Rendering)** — 빈 HTML을 받고 브라우저의 JS가 화면을 만듦.
- **hydration** — SSR로 받은 HTML에 JS가 이벤트·상태를 붙여 **살아 움직이게 만드는 과정**. 정상 동작의 이름이다. 마네킹(HTML)에 사람(JS)이 들어가 움직이는 것.
- **hydration mismatch(hydration error)** — hydration 도중 "서버가 그린 HTML"과 "클라이언트가 같은 코드로 다시 계산한 결과"가 **다른 것**. 버그의 이름은 이쪽이다. 마네킹 자세와 들어간 사람 자세가 안 맞는 셈.

**원인** — 서버와 브라우저에서 **같은 코드가 다른 값을 내는 경우**
- 실행 시점·환경 차이: `new Date()`, `Math.random()`, 서버와 사용자 타임존 차이
- 브라우저에만 있는 값: `window`, `localStorage`, 화면 너비
- 잘못된 HTML 중첩: `<p>` 안에 `<div>`, `<a>` 안에 `<a>` — 브라우저가 HTML을 고쳐 읽어 구조가 달라짐
- 브라우저 확장 프로그램(번역기, 비밀번호 관리자)이 DOM을 먼저 건드림

**지시 예문**
- "날짜 표시에서 hydration mismatch가 나. 서버에선 자리만 그리고, 실제 시간은 마운트 후 클라이언트에서 채워줘."
- "localStorage 값으로 테마를 정하다가 hydration error가 나. 서버와 첫 렌더 결과가 같도록 고쳐줘."
- "hydration error 원인이 잘못된 HTML 중첩인지 먼저 확인해줘 (p 안의 div 등)."

## Virtualization

**현상** — 주문 내역·로그·채팅처럼 행이 수천 개인 목록에 들어가면 첫 화면이 늦게 뜨고, 스크롤이 버벅이며, 필터를 눌러도 반응이 굼뜨다(INP 악화).

**용어**
- **virtualization(가상화, windowing)** — 목록 전체를 DOM에 그리지 않고 **지금 화면에 보이는 행 + 약간의 여유분만** 그리는 기법. 스크롤하면 화면 밖으로 나간 행을 지우고 새로 보일 행을 그린다. 전체 높이만큼의 빈 공간은 유지해서 스크롤바는 정상처럼 보인다.
- 비유: 영화 세트장. 거리 전체를 짓지 않고 카메라에 잡히는 건물 앞면만 세운다. 카메라가 움직이면 그쪽 세트만 새로 세운다.
- **overscan** — 빠르게 스크롤할 때 빈칸이 보이지 않도록 화면 위아래에 미리 그려두는 여유 행 수.
  - 필요한 이유는 행 크기가 아니라 **타이밍 차이**다. 스크롤 자체는 브라우저가 main thread와 별도로 즉시 움직이지만, 새 행을 그리는 건 JS(main thread)라 한 박자 늦다. 그 틈에 아직 안 그린 영역이 드러나 흰 빈칸이 번쩍인다. overscan은 미리 그려둔 행으로 이 틈을 메운다.
  - 트레이드오프: 크게 잡을수록 빈칸은 줄지만 그리는 행이 늘어 virtualization 효과가 줄어든다. 보통 화면 위아래로 몇 행 정도.
  - 세트장 비유로는, 카메라가 빠르게 돌면 세트 짓는 속도가 못 따라가니 옆 건물 몇 채를 미리 세워두는 것.
- 대표 라이브러리: TanStack Virtual, react-window, react-virtuoso

**부작용** — 지시할 때 같이 챙길 것
- 브라우저 찾기(Ctrl+F)로 화면 밖 행을 못 찾는다 — 아직 DOM에 없으니까
- 행 높이가 제각각이면 스크롤 위치가 튀거나 계산이 복잡해진다
- 스크린리더가 전체 개수를 모를 수 있다

**대안** — 수백 개 수준이면 virtualization까지 필요 없을 수 있다. 페이지네이션, 무한 스크롤, CSS `content-visibility: auto`가 더 단순한 선택지다.

**지시 예문**
- "주문 목록이 3천 행이라 스크롤이 버벅여. virtualization 적용해줘. 행 높이는 고정 64px이야."
- "채팅 목록에 virtualization 넣어줘. 메시지 길이에 따라 높이가 달라서 가변 높이를 지원해야 해."
- "목록이 200개 정도인데 virtualization이 꼭 필요한지, content-visibility로 충분한지 먼저 판단해줘."

## FOUC · FOUT · FOIT

**현상** — 페이지가 뜨는 순간 잠깐 이상한 모습이 보였다가 정상으로 바뀐다. 스타일 없는 맨 HTML이 번쩍이거나, 글꼴이 바뀌며 글자가 출렁이거나, 다크 모드인데 흰 화면이 번쩍인다.

**용어** — 전부 "Flash of ~"(~가 번쩍임)의 약자다.
- **FOUC (Flash of Unstyled Content)** — CSS가 적용되기 전의 **맨 HTML**이 잠깐 보임. CSS를 늦게 붙이거나 JS로 스타일을 주입할 때 생긴다.
- **FOUT (Flash of Unstyled Text)** — 웹폰트가 오기 전 **대체 글꼴**로 먼저 보였다가 바뀜. 글자 폭이 달라 줄바꿈이 바뀌면 layout shift(CLS)로 이어진다.
- **FOIT (Flash of Invisible Text)** — 웹폰트가 올 때까지 **글자가 아예 안 보임**. 버튼·제목 자리가 비어 보인다.
- FOUT와 FOIT는 `font-display` 속성으로 고른다. `swap`이면 FOUT(일단 보여줌), `block`이면 FOIT(기다림). 보통 FOUT가 낫다 — 안 보이는 것보다 다른 글꼴이라도 보이는 게 낫기 때문.
- **다크 모드 깜빡임(flash of incorrect theme)** — FOUC의 친척. 저장된 테마를 JS가 늦게 읽어서, 첫 화면이 기본(라이트) 테마로 그려졌다가 다크로 바뀐다.

**원인** — 공통점은 **첫 화면을 그리는 시점에 필요한 정보(CSS·폰트·테마)가 아직 없음**.

**외울 것** — 약자 셋을 다 외울 필요는 없다. 지시할 때는 **"flash" + 무엇이 번쩍이는지**만 말하면 AI가 약자로 바꿔 알아듣는다. 약자는 AI 답변·문서를 읽을 때 알아보는 정도면 충분하다.
- 스타일 없는 화면이 flash → FOUC
- 다른 글꼴이 flash → FOUT
- 글자가 안 보이다 나타남 → FOIT (이건 "번쩍"보다 "빈칸"이라 따로 말해야 한다)
- 테마가 flash → 다크 모드 깜빡임

**지시 예문**
- "새로고침할 때 다크 모드인데 흰 화면이 번쩍여. 테마를 <head>의 인라인 스크립트에서 첫 paint 전에 적용해줘."
- "웹폰트 로드 때 FOUT로 줄바꿈이 바뀌어. 대체 글꼴 크기를 웹폰트에 맞춰서(size-adjust) layout shift를 없애줘."
- "제목 글자가 1~2초 안 보이다 나타나. FOIT 같으니 font-display: swap으로 바꾸고 폰트를 preload해줘."

## Scroll chaining과 scroll lock

**현상**
- 모달 안의 목록을 끝까지 스크롤했는데, 계속 굴리니 **뒤 배경 페이지가 대신 스크롤**된다.
- 모달을 열면 뒤 페이지가 **옆으로 살짝 움찔**한다.

**용어**
- **scroll chaining** — 안쪽 스크롤 영역이 끝에 닿으면 남은 스크롤이 **바깥(부모·페이지)으로 넘어가는** 브라우저 기본 동작. 버그가 아니라 기본값이라서 막아야 한다.
  - CSS `overscroll-behavior: contain`을 안쪽 영역에 주면 넘어가지 않는다.
  - 비유: 위층 욕조가 넘치면 아래층으로 물이 샌다. `contain`은 욕조 둘레에 턱을 세우는 것.
- **scroll lock(body scroll lock)** — 모달·드로어가 열려 있는 동안 **뒤 페이지 스크롤을 아예 막는 것**. 보통 `body`에 `overflow: hidden`을 건다. 모바일 Safari는 동작이 달라 실제 기기에서 따로 확인해야 한다.
- **scrollbar shift** — scroll lock으로 스크롤바가 사라지면 그 폭(데스크톱 기준 보통 15px 안팎)만큼 페이지가 넓어지면서 **내용이 옆으로 밀리는** 현상. 옆으로 움찔하는 원인이 이것이다. layout shift의 일종.
  - `scrollbar-gutter: stable`로 스크롤바 자리를 항상 비워두거나, 사라진 폭만큼 `padding-right`를 보충해 막는다.

**원인 정리**
- 배경이 스크롤됨 → scroll chaining (또는 scroll lock 없음)
- 모달 열 때 옆으로 움찔 → scroll lock이 만든 scrollbar shift

**지시 예문**
- "모달 안 목록 끝에서 배경이 스크롤돼. 목록에 overscroll-behavior: contain 걸고, 모달 열린 동안 body scroll lock 해줘."
- "모달 열 때 페이지가 옆으로 움찔해. scroll lock 때문에 생긴 scrollbar shift니까 scrollbar-gutter: stable로 막아줘."

## 텍스트 넘침과 줄바꿈

**현상**
- 한글 문장이 "안녕하세 / 요"처럼 **단어 중간에서 끊겨** 줄바꿈된다.
- 긴 URL·영문 단어가 카드 밖으로 **삐져나간다**.
- 제목이 길어 카드 높이가 제각각이 된다. 말줄임(…)을 걸었는데 flex 안에서는 안 먹는다.

**용어**
- **truncate(말줄임, ellipsis)** — 한 줄을 넘는 텍스트를 `…`로 자르기. `overflow: hidden` + `white-space: nowrap` + `text-overflow: ellipsis` 세 개가 함께 있어야 동작한다. Tailwind에서는 `truncate`.
- **line clamp** — 정해진 **여러 줄**까지만 보여주고 `…`로 자르기. "2줄까지만" 같은 요구. Tailwind에서는 `line-clamp-2`.
- **`word-break: keep-all`** — 한글·중국어·일본어(CJK)는 기본값이 **글자 단위 줄바꿈**이라 단어가 쪼개진다. `keep-all`은 영어처럼 **띄어쓰기 단위**로만 끊는다. 한국어 서비스에서 거의 기본으로 건다.
- **`overflow-wrap: anywhere`(또는 `break-word`)** — 띄어쓰기 없는 긴 URL·영문을 **필요하면 중간에서라도 끊어** 영역 밖으로 나가지 않게 함. `keep-all`과 함께 쓰면 "평소엔 단어 단위, 너무 길면 강제로 끊기"가 된다.
- **`min-width: 0`** — flex 자식은 기본적으로 **내용보다 작아지지 않으려** 한다(`min-width: auto`). 그래서 flex 안에서는 truncate가 안 먹고 부모를 밀어낸다. 자식에 `min-width: 0`(Tailwind `min-w-0`)을 주면 줄어들 수 있게 되어 말줄임이 동작한다.

**지시 예문**
- "본문 한글이 단어 중간에서 끊겨. word-break: keep-all 적용하고, 긴 URL은 overflow-wrap: anywhere로 넘치지 않게 해줘."
- "카드 제목은 2줄 line clamp, 설명은 1줄 truncate로 맞춰서 카드 높이를 통일해줘."
- "flex 행 안의 파일명에 truncate가 안 먹고 버튼을 밀어내. 파일명 쪽에 min-width: 0 줘줘."

## Skeleton · spinner · optimistic UI

**현상**
- 데이터를 불러오는 동안 화면이 텅 비었다가 한 번에 뜬다. 또는 뜨면서 내용이 밀린다.
- 응답이 금방 오는데도 스피너가 0.1초 번쩍이고 사라져 오히려 거슬린다.
- 좋아요를 누르면 서버 응답을 기다리느라 하트가 한 박자 늦게 채워진다.

**용어** — 모두 "기다림을 어떻게 보여줄까"에 대한 선택지다.
- **spinner** — 빙글빙글 도는 표시. **얼마나 걸릴지 모를 때**, 버튼·작은 영역의 짧은 작업에 쓴다.
- **progress bar** — 진행률 막대. **얼마나 남았는지 알 수 있을 때**(파일 업로드 등) 쓴다.
- **skeleton** — 실제 콘텐츠 모양을 회색 상자로 미리 그려둔 자리표시. 목록·카드·프로필처럼 **화면 영역을 채우는 로딩**에 쓴다. 체감 대기가 줄고, 실제 콘텐츠와 크기를 맞추면 layout shift(CLS)도 막는다.
- **optimistic UI(낙관적 업데이트)** — 서버 응답을 기다리지 않고 **성공했다고 가정하고 화면부터 바꾸는** 방식. 실패하면 원래대로 되돌리고(rollback) 알린다.
  - 비유: 카카오톡 메시지. 보내자마자 말풍선이 뜨고, 전송 실패하면 그제야 빨간 느낌표가 붙는다.
  - 좋아요·북마크·체크박스처럼 **거의 실패하지 않고 되돌리기 쉬운** 동작에만 쓴다. 결제·삭제처럼 실패하면 곤란한 동작엔 쓰지 않는다.
- **spinner 지연 표시** — 응답이 빠르면 스피너를 아예 안 보여주도록 일정 시간(예: 300ms) 뒤에만 띄우는 요령. 번쩍임을 막는다.

**지시 예문**
- "상품 목록 로딩 중에 화면이 비어. 카드 크기와 같은 skeleton으로 바꿔서 CLS도 같이 막아줘."
- "좋아요 버튼을 optimistic UI로 바꿔줘. 요청 실패 시 rollback하고 토스트로 알려줘."
- "저장 버튼 스피너가 번쩍여. 300ms 넘게 걸릴 때만 스피너를 보여줘."

## Cache와 cache invalidation

**현상**
- 글을 수정·삭제했는데 목록으로 돌아가면 **예전 내용이 그대로** 보인다. 새로고침해야 바뀐다.
- 새로 배포했는데 내 브라우저에서만 **옛 화면**이 보인다.
- 로컬에선 바로 반영되는데 배포 환경에선 몇 분 뒤에야 반영된다.

**용어**
- **cache(캐시)** — 한 번 받은 결과를 저장해두고 다음엔 다시 묻지 않고 꺼내 쓰는 것. 빠르지만 **원본이 바뀌어도 모른다**.
  - 비유: 휴대폰 연락처. 친구가 번호를 바꿔도 내 폰엔 옛 번호가 남아 있다.
- **stale data** — 캐시에 남은 **낡은 데이터**. 앞서 배운 stale response와 같은 "stale(상한)"이다.
- **cache invalidation(캐시 무효화)** — "이 캐시는 이제 낡았으니 다음엔 새로 받아와"라고 표시하는 것. 데이터를 바꾼 직후 관련 캐시를 무효화해야 화면이 맞는다.
- **revalidate** — 캐시를 새 데이터로 다시 채우는 것. Next.js의 `revalidatePath`·`revalidateTag`, TanStack Query의 `invalidateQueries`가 이 역할이다.
- **캐시는 여러 층에 있다** — 어느 층 문제인지 짚어야 지시가 정확해진다.
  - 브라우저 캐시: 내 브라우저만 옛것을 봄 → 강력 새로고침(Cmd+Shift+R)으로 확인
  - CDN 캐시: 배포 후 모든 사용자가 한동안 옛것을 봄
  - 서버 데이터 캐시: Next.js 등 프레임워크가 서버에서 보관한 결과
  - 클라이언트 데이터 캐시: TanStack Query·SWR이 브라우저 메모리에 보관한 결과

**원인** — 데이터를 바꾸는 코드(mutation)는 있는데, 그 데이터를 보여주는 **캐시를 무효화하는 코드가 없음**.

**지시 예문**
- "글 수정 후 목록에 옛 제목이 보여. 수정 성공 시 목록 쿼리를 invalidate해줘."
- "Next.js server action에서 글 삭제 후 /posts 페이지가 갱신 안 돼. revalidatePath로 캐시 무효화해줘."
- "배포 후 일부 사용자만 옛 화면을 봐. 브라우저 캐시인지 CDN 캐시인지 먼저 구분해줘."

## CORS

**현상** — 프론트에서 API를 호출하면 콘솔에 빨간 에러가 뜬다: "Access to fetch at ... has been blocked by CORS policy". 그런데 **같은 주소를 Postman·curl로 부르면 멀쩡히 응답**이 온다.

**용어**
- **origin(출처)** — `프로토콜 + 도메인 + 포트` 세 개의 묶음. 하나라도 다르면 다른 출처다. `localhost:3000`과 `localhost:8000`도 서로 다른 출처.
- **same-origin policy(동일 출처 정책)** — 브라우저는 기본적으로 **다른 출처의 응답을 JS가 읽지 못하게** 막는다. 악성 사이트가 내 로그인 정보로 은행 API를 몰래 읽는 걸 막기 위한 보안 장치.
- **CORS (Cross-Origin Resource Sharing)** — 서버가 응답 헤더(`Access-Control-Allow-Origin`)로 "이 출처는 읽어도 돼"라고 **허락해주는 규칙**. 허락이 없으면 브라우저가 응답을 버린다.
  - 비유: 아파트 경비실. 방문객(다른 출처)은 입주민(서버)이 방문 명단에 올려야 들어갈 수 있고, 막는 건 경비(브라우저)다. Postman엔 경비가 없어서 그냥 통과한다.
- **preflight** — JSON 전송·커스텀 헤더·PUT/DELETE 같은 요청 전에 브라우저가 `OPTIONS` 요청으로 먼저 "보내도 되나요?" 묻는 것. 서버가 OPTIONS에 제대로 답하지 않으면 본 요청은 아예 나가지 않는다.

**원인** — **서버가 허락 헤더를 안 보냄**. 그래서 고칠 곳은 프론트가 아니라 서버(또는 프록시)다.
- 흔한 잘못된 처방: 프론트에서 `mode: 'no-cors'` → 에러는 사라지지만 응답 내용을 못 읽는다.
- 쿠키를 함께 보낼 때는 `Access-Control-Allow-Origin: *`(전부 허용)가 안 된다. 출처를 정확히 적어야 한다.

**지시 예문**
- "localhost:3000에서 API(localhost:8000) 호출 시 CORS 에러가 나. 서버에서 3000 출처를 허용하고 preflight(OPTIONS)도 처리해줘."
- "CORS 에러를 프론트에서 우회하지 말고, Next.js rewrites로 같은 출처 프록시를 만들어줘."
- "쿠키 인증 요청에서만 CORS 에러가 나. credentials 설정과 Allow-Origin이 *인지 확인해줘."

## Re-render와 무한 루프

**현상**
- 화면이 멈추고 콘솔에 "Too many re-renders" 또는 "Maximum update depth exceeded" 에러가 뜬다.
- 네트워크 탭에 **같은 API 요청이 끝없이** 찍힌다.
- 입력창 한 글자 칠 때마다 상관없는 영역까지 버벅인다.

**용어** (React 기준)
- **render / re-render** — 컴포넌트 함수를 다시 실행해 화면을 새로 계산하는 것. **state·props가 바뀌거나, 부모가 re-render되면** 일어난다.
- **불필요한 re-render** — 바뀐 게 없는데 다시 계산되는 것. 많아지면 INP가 나빠진다.
- **무한 루프(infinite re-render)** — re-render가 state를 바꾸고, 그게 또 re-render를 부르는 순환. React가 일정 횟수에서 강제로 멈추며 위 에러를 낸다.
- **dependency array(의존성 배열)** — `useEffect(fn, [a, b])`의 `[a, b]`. "a나 b가 바뀌면 fn을 다시 실행해"라는 뜻.
- **참조 동일성(referential equality)** — 객체·배열·함수는 **내용이 같아도 새로 만들면 다른 것**으로 취급된다(`{} !== {}`). 컴포넌트 안에서 만든 객체는 render마다 새로 만들어진다.
  - 비유: 같은 내용으로 명함을 새로 인쇄해도 "새 명함"이다. React는 내용이 아니라 "같은 종이인가"를 본다.

**원인** — 무한 루프의 전형
1. `useEffect`의 의존성 배열에 **render마다 새로 만들어지는 객체·함수**가 들어감
2. 그래서 매 render마다 "바뀌었다"고 판단해 effect 실행 → effect 안에서 `setState` → re-render → 1로 돌아감

**지시 예문**
- "목록 API가 무한으로 호출돼. useEffect 의존성 배열에 매 render마다 새로 생기는 객체가 있는지 확인하고 고쳐줘."
- "Maximum update depth exceeded 에러가 나. setState가 render나 effect에서 순환하는 지점을 찾아줘."
- "입력할 때 사이드바까지 re-render돼. React DevTools로 불필요한 re-render를 찾아서 줄여줘."

## 모바일 viewport: 100vh 문제와 safe area

**현상**
- 데스크톱에선 화면에 딱 맞던 풀스크린 영역이, 모바일에선 **하단이 잘려** 고정 버튼이 주소창 뒤로 숨는다.
- 스크롤하면 주소창이 접히면서 레이아웃이 **들썩**인다.
- 아이폰에서 하단 고정 버튼이 **홈 인디케이터(하단 막대)와 겹치거나**, 상단 내용이 노치에 가린다.

**용어**
- **viewport** — 브라우저에서 실제로 페이지가 보이는 창 영역.
- **`100vh` 문제** — 모바일 브라우저는 주소창·툴바가 나타났다 사라지는데, `vh`는 **툴바가 사라진 가장 큰 상태** 기준이다. 그래서 툴바가 보일 땐 `100vh`가 실제 보이는 높이보다 커서 아래가 잘린다.
- **새 viewport 단위** — 이 문제를 풀려고 생긴 단위들:
  - `svh` (small) — 툴바가 **보일 때** 높이. 절대 안 잘림. 기본 선택.
  - `lvh` (large) — 툴바가 **숨었을 때** 높이. 기존 `vh`와 같다.
  - `dvh` (dynamic) — 툴바 상태에 따라 **실시간으로 변함**. 딱 맞지만 스크롤 중 레이아웃이 들썩일 수 있다.
- **safe area** — 노치·둥근 모서리·홈 인디케이터를 피한, 내용을 안전하게 놓을 수 있는 영역. CSS `env(safe-area-inset-bottom)` 등으로 그 여백 크기를 받는다. viewport meta에 `viewport-fit=cover`가 있어야 값이 들어온다.
  - 비유: 액자 유리 가장자리를 덮는 테두리(매트). 그림을 그 안쪽에 둬야 안 가린다.

**지시 예문**
- "모바일에서 풀스크린 섹션 하단이 잘려. 100vh를 100svh로 바꿔줘."
- "하단 고정 결제 버튼이 아이폰 홈 인디케이터와 겹쳐. padding-bottom에 env(safe-area-inset-bottom)을 더해줘."
- "dvh 때문에 스크롤 중 레이아웃이 들썩여. 들썩임이 없어야 하는 영역은 svh로 바꿔줘."

## 인터랙션 상태: hover · active · focus-visible

**현상**
- 모바일에서 버튼을 탭한 뒤 **hover 색이 그대로 남아** 선택된 것처럼 보인다.
- 버튼을 마우스로 클릭하면 **파란 테두리**가 생겨서 거슬린다. 그래서 없앴더니 키보드(Tab)로 이동할 때 지금 어디에 있는지 안 보인다.
- 버튼을 눌러도 눌렸다는 느낌이 없다.

**용어** — 요소가 사용자 동작에 따라 가지는 **상태(state)**. 디자인 시안에서도 같은 이름으로 부른다.
- **hover** — 마우스를 올려둔 상태.
- **active(pressed)** — 누르고 있는 순간. 살짝 어두워지거나 작아지면 "눌렸다"는 피드백이 된다.
- **focus** — 키보드 입력을 받을 대상으로 선택된 상태. 클릭·Tab 모두로 생긴다.
- **focus-visible** — focus 중 **키보드로 이동했을 때만** 표시하는 상태. 마우스 클릭엔 테두리(focus ring)를 숨기고 Tab 이동엔 보여준다.
- **disabled** — 비활성. 흐리게 + 클릭 불가.
- **sticky hover** — 터치 기기엔 마우스가 없는데, 탭하면 브라우저가 hover를 흉내 내고 **다른 곳을 탭할 때까지 유지**하는 현상. `@media (hover: hover)` 안에서만 hover 스타일을 주면 막힌다. (Tailwind v4의 `hover:`는 기본으로 이렇게 동작한다.)

**원인**
- sticky hover → hover 스타일을 터치 기기 구분 없이 줌
- 파란 테두리 문제 → `:focus`에 스타일을 줘서 클릭에도 보임. `outline: none`으로 통째로 지우면 키보드 사용자가 길을 잃는다(접근성 문제).

**지시 예문**
- "모바일에서 탭 후 hover 색이 남아. hover 스타일을 hover 가능한 기기에서만 적용해줘."
- "클릭할 때 focus ring이 거슬려. outline 지우지 말고 focus-visible일 때만 보이게 바꿔줘."
- "버튼에 active 상태가 없어서 눌린 느낌이 안 나. 누를 때 살짝 작아지게(scale 0.97) 해줘."

## 환경 변수(env)

**현상**
- 로컬에선 잘 되는데 **배포하면 API 호출이 실패**한다. 로그를 보면 키 값이 `undefined`.
- `.env` 값을 바꿨는데 **반영이 안 된다**.
- 브라우저에서 `process.env.API_KEY`를 읽으면 `undefined`가 나온다.

**용어**
- **환경 변수(environment variable, env)** — API 키·DB 주소처럼 **코드 밖에 두는 설정값**. 같은 코드를 로컬·스테이징·프로덕션에서 다른 값으로 돌리기 위해 쓴다.
- **`.env` / `.env.local`** — 로컬용 환경 변수 파일. 비밀값이 들어가므로 **git에 올리지 않는다**. 그래서 배포 환경(Vercel 등)에는 **따로 등록**해야 한다 — "로컬에선 되는데 배포하면 안 됨"의 1순위 원인.
- **public 접두사** — 브라우저 코드에서 읽을 수 있는 변수는 이름에 표시를 붙인다. Next.js는 `NEXT_PUBLIC_`, Vite는 `VITE_`. 접두사가 없으면 서버에서만 읽힌다.
- **build time 주입** — public 변수는 **빌드할 때 값이 코드에 박힌다**. 그래서 값을 바꾸면 dev 서버 재시작·재배포(재빌드)를 해야 반영된다.
- **secret 노출** — public 접두사를 붙인 값은 **누구나 브라우저 개발자 도구로 볼 수 있다**. 결제·DB·OpenAI 같은 비밀 키에 붙이면 키가 유출된다.
  - 비유: public 변수는 명함에 인쇄한 정보다. 전화번호는 괜찮지만 금고 비밀번호를 인쇄하면 안 된다.

**지시 예문**
- "배포 환경에서만 API 키가 undefined야. Vercel에 환경 변수가 등록됐는지, 이름이 로컬과 같은지 확인해줘."
- "이 키가 NEXT_PUBLIC_으로 브라우저에 노출되고 있어. 서버(API route)에서만 쓰도록 옮기고 접두사 빼줘."
- "env를 바꿨는데 반영이 안 돼. build time 주입 변수인지 확인하고 재빌드가 필요한지 알려줘."

## URL 상태와 scroll restoration

**현상**
- 목록에서 필터·정렬·페이지를 골라뒀는데 **새로고침하면 초기화**된다. 링크를 공유해도 상대는 기본 화면을 본다.
- 상세 페이지에서 **뒤로가기**하면 목록이 맨 위로 올라가 있다. 무한 스크롤로 한참 내려갔던 위치가 사라진다.
- 검색창에 글자 칠 때마다 방문 기록이 쌓여서, 뒤로가기를 열 번 눌러야 이전 페이지로 간다.

**용어**
- **URL 상태(URL state)** — 화면 상태를 메모리(`useState`)가 아니라 **주소에 적어두는 것**. 새로고침·공유·뒤로가기에 살아남는다. 쇼핑몰 필터처럼 "이 화면을 다시 보고 싶은" 상태에 쓴다.
  - 비유: 메모리 상태는 머릿속 기억, URL 상태는 포스트잇. 잠들면(새로고침) 기억은 날아가지만 포스트잇은 남고, 남에게 건네줄 수도 있다.
- **query string(search params)** — 주소의 `?` 뒤 부분. `/products?category=shoes&sort=price&page=2`. 필터·정렬·페이지·검색어를 담는 자리.
- **path params** — 주소 경로 자체에 들어간 값. `/products/123`의 `123`. "무엇을 보는가(대상)"는 path, "어떻게 보는가(조건)"는 query로 나누는 게 관례.
- **push vs replace** — 주소를 바꿀 때 방문 기록에 **새 칸을 추가(push)**할지, **현재 칸을 덮어쓸(replace)**지. 검색어 입력·슬라이더처럼 자주 바뀌는 값은 replace로 해야 뒤로가기가 꼬이지 않는다.
- **scroll restoration** — 뒤로가기 때 **이전 스크롤 위치를 되돌려주는 것**. 브라우저가 기본으로 해주지만, 데이터를 뒤늦게 불러오는 목록(특히 무한 스크롤)은 복원 시점에 내용이 아직 없어서 실패한다.

**지시 예문**
- "상품 목록의 필터·정렬·페이지를 query string으로 옮겨서 새로고침·공유해도 유지되게 해줘."
- "검색어 입력 시 URL을 replace로 바꿔서 방문 기록이 쌓이지 않게 해줘."
- "상세에서 뒤로가기하면 무한 스크롤 목록이 맨 위로 가. 불러온 데이터를 캐시해서 scroll restoration이 되게 해줘."

## Semantic HTML과 접근성(a11y)

**현상**
- 클릭은 되는데 **Tab으로 이동이 안 되고 Enter로 눌리지 않는** 버튼이 있다.
- 링크처럼 생긴 메뉴를 **Cmd+클릭해도 새 탭으로 안 열린다**. 우클릭에 "새 탭에서 열기"가 없다.
- 체크박스 옆 글자를 눌러도 체크가 안 된다. 작은 체크박스만 정확히 눌러야 한다.
- 아이콘만 있는 버튼을 스크린리더가 그냥 "버튼"이라고만 읽는다.

**용어**
- **semantic HTML(의미 있는 HTML)** — 모양이 아니라 **역할에 맞는 태그**를 쓰는 것. `<button>`, `<a>`, `<nav>`, `<main>`, `<label>` 등. 역할에 맞는 태그를 쓰면 키보드 조작·스크린리더·검색엔진 지원이 **공짜로** 따라온다.
  - 반대말 격인 **div soup** — 전부 `<div onClick>`으로 만든 상태. 보기엔 같아도 위 기능이 전부 빠진다.
  - **별도 언어가 아니다.** semantic HTML도 그냥 HTML이다. 같은 HTML 안에서 **태그를 고르는 방식**을 가리키는 말이다.
  - 비유: 워드에서 제목을 만들 때 "글자 크게 + 굵게"로 꾸미는 것과 "제목 1" 스타일을 적용하는 것. 화면엔 똑같이 보이지만, **목차 자동 생성·탐색 창**은 "제목 1"을 쓴 쪽에서만 동작한다. 워드가 "이게 제목이다"를 알기 때문이다. 브라우저도 같다 — `<div>`를 버튼처럼 꾸미면 모양만 버튼이고, `<button>`이어야 브라우저가 "이건 버튼"임을 알고 키보드·스크린리더 기능을 붙여준다.
  - 예:
    ```html
    <!-- 겉모습만 버튼: Tab·Enter 안 됨, 스크린리더는 "그룹" 정도로 읽음 -->
    <div class="btn" onclick="save()">저장</div>

    <!-- 역할까지 버튼: Tab·Enter·Space 자동 지원, "저장, 버튼"으로 읽음 -->
    <button class="btn" onclick="save()">저장</button>
    ```
- **button vs a** — `<a href>`는 **어딘가로 이동**(주소가 바뀜), `<button>`은 **동작 실행**(저장·열기·삭제). 이동인데 button을 쓰면 새 탭 열기가 안 되고, 동작인데 a를 쓰면 이상한 기록이 남는다.
- **label** — 입력창·체크박스에 붙는 이름표. `<label>`로 연결하면 **글자를 눌러도** 해당 입력이 선택되고(터치 영역 확대), 스크린리더가 이름을 읽는다.
- **aria-label** — 눈에 보이는 글자가 없는 요소(아이콘 버튼)에 **스크린리더용 이름**을 붙이는 속성. `<button aria-label="닫기">✕</button>`.
- **alt** — 이미지의 대체 텍스트. 내용 있는 이미지는 설명을, 장식용 이미지는 `alt=""`(빈 값)를 준다.
- **a11y** — accessibility의 줄임말. a와 y 사이 글자가 11개라서.

**지시 예문**
- "div onClick으로 만든 버튼들을 button 태그로 바꿔서 키보드로도 누를 수 있게 해줘."
- "사이드바 메뉴가 button이라 새 탭으로 안 열려. 페이지 이동이니까 a(Link)로 바꿔줘."
- "아이콘 전용 버튼에 aria-label 붙이고, 체크박스는 label로 감싸서 글자를 눌러도 체크되게 해줘."

## Bundle과 code splitting

**현상**
- 첫 페이지 하나 여는 데 JS를 몇 MB씩 받는다. 느린 폰에서 화면은 떴는데 한동안 **눌러도 반응이 없다**.
- 차트 라이브러리 하나 추가했더니 **모든 페이지**가 느려졌다.
- 날짜 함수 하나 쓰려고 라이브러리를 넣었는데 용량이 크게 늘었다.

**용어**
- **bundle(번들)** — 여러 JS 파일과 라이브러리를 브라우저용으로 **묶어놓은 결과 파일**. 빌드 도구(webpack, Turbopack, Vite)가 만든다.
- **bundle size** — 그 묶음의 용량. 크면 받는 시간 + **해석·실행 시간**이 늘어 LCP·INP가 함께 나빠진다. 느린 폰일수록 실행 시간이 더 아프다.
- **code splitting** — 하나의 큰 묶음을 **여러 조각으로 나눠 필요할 때 받게** 하는 것. Next.js 등은 페이지 단위로 자동으로 나눈다.
  - 비유: 이삿짐. 전부 한 트럭에 실어 다 내려야 입주할 수 있는 대신, 당장 필요한 짐만 먼저 들이고 나머지는 나중에 받는 것.
- **dynamic import(lazy loading 컴포넌트)** — 특정 컴포넌트를 **실제로 필요해질 때** 불러오는 것. 모달 안의 에디터, 탭 뒤의 차트처럼 첫 화면에 안 보이는 무거운 것에 쓴다. `next/dynamic`, `React.lazy`.
- **tree shaking** — 라이브러리에서 **실제로 쓴 부분만 남기고** 나머지를 빌드에서 털어내는 것. 라이브러리 구조·import 방식에 따라 안 될 때가 있다.
- **bundle analyzer** — 번들 안에 무엇이 얼마나 차지하는지 **지도처럼 보여주는 도구**. 추측 대신 이걸로 범인을 찾는다.

**지시 예문**
- "bundle analyzer로 번들에서 가장 큰 라이브러리 5개를 찾아줘."
- "차트 컴포넌트가 대시보드 탭에서만 쓰여. dynamic import로 바꿔서 다른 페이지 번들에서 빼줘."
- "날짜 처리에 쓰는 라이브러리가 너무 커. tree shaking 되는 가벼운 대안이나 내장 Intl API로 바꿔줘."
