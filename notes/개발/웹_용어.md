## Layout shift와 CLS

**현상** — 글을 읽는데 위쪽 이미지·광고가 늦게 뜨면서 본문이 갑자기 아래로 밀린다. 버튼을 누르려는 순간 버튼이 밀려 엉뚱한 걸 누르게 된다.

**용어**
- **layout shift** — 이미 화면에 보이던 요소가 예고 없이 위치를 옮기는 현상 하나하나.
- **CLS (Cumulative Layout Shift)** — 페이지가 살아 있는 동안 생긴 layout shift를 점수로 매긴 지표. Core Web Vitals 세 지표 중 하나. **0.1 이하**면 "좋음"이다.
- 클릭·키 입력 직후(0.5초 이내)에 생긴 이동은 사용자가 예상한 변화로 보고 CLS에 넣지 않는다. 아코디언을 눌러 펼친 것은 layout shift로 치지 않는다.

**원인** — 공통점은 **자리를 미리 잡아두지 않은 요소가 나중에 끼어드는 것**이다. 식당에서 일행 자리를 안 맡아두면 늦게 온 사람이 끼어 앉을 때 모두가 한 칸씩 밀려나는 것과 같다.
- `width`/`height`(또는 `aspect-ratio`)를 지정하지 않은 이미지·영상·iframe
- 늦게 삽입되는 배너·광고·쿠키 안내
- 웹폰트가 늦게 로드돼 글자 폭이 바뀌면서 줄바꿈이 달라짐

**지시 예문**
- "히어로 이미지에 width/height를 지정해서 로드 전에 공간을 예약하고, CLS를 없애줘."
- "상단 공지 배너가 늦게 들어와 본문을 밀어내. 배너 자리를 min-height로 미리 잡아줘."
- "웹폰트 교체 때 layout shift가 생겨. 폴백 폰트 크기를 맞춰서 줄바꿈이 안 바뀌게 해줘."

## LCP

**현상** — 페이지에 들어가면 헤더·메뉴는 금방 뜨는데, 정작 화면 한가운데 큰 대표 이미지(또는 큰 제목)가 한참 뒤에 나타난다. "페이지가 느리다"는 체감의 대부분이 이것이다.

**용어**
- **LCP (Largest Contentful Paint)** — 첫 화면(viewport) 안에서 **가장 큰 이미지나 텍스트 덩어리**가 그려진 시점. 페이지 로드 시작부터 잰다. Core Web Vitals 세 지표 중 하나이며 **2.5초 이하**면 "좋음"이다.
- 후보: `<img>`, 영상 poster, CSS `background-image`, 큰 텍스트 블록(제목·문단). 대개 히어로 이미지가 LCP 요소가 된다.
- 식당에 비유하면 반찬이 먼저 깔리는 건 상관없고, **메인 요리가 나온 시각**을 재는 것이다.

**원인**
- 서버 응답 자체가 느림 (HTML이 늦게 옴)
- 렌더링을 막는 CSS·JS가 먼저 다 받아져야 그림을 그리기 시작함
- 히어로 이미지가 너무 무겁거나(원본 PNG 등) 늦게 발견됨
- 히어로 이미지에 `loading="lazy"`를 걸어 오히려 늦게 받음 — 흔한 실수
- 클라이언트 렌더링(CSR)이라 JS 실행이 끝나야 본문이 생김

**지시 예문**
- "히어로 이미지가 LCP 요소야. lazy loading 빼고 `fetchpriority="high"`로 우선 로드해줘."
- "LCP 이미지를 WebP/AVIF로 바꾸고 화면 크기에 맞는 사이즈만 받게 해줘."
- "LCP가 3초 넘게 나와. 원인이 서버 응답인지, 이미지인지, 렌더 블로킹 리소스인지 먼저 분석해줘."

## INP

**현상** — 버튼을 눌렀는데 0.5초쯤 아무 반응이 없다가 뒤늦게 바뀐다. 입력창에 타이핑하면 글자가 한 박자 늦게 찍힌다. 그래서 같은 버튼을 두세 번 누르게 된다.

**용어**
- **INP (Interaction to Next Paint)** — 클릭·탭·키 입력 후 **화면에 다음 변화가 그려지기까지 걸린 시간**. 스크롤·hover는 재지 않는다. 페이지에서 일어난 상호작용 중 거의 가장 느린 것을 대표값으로 쓴다. Core Web Vitals 세 지표 중 하나이며 **200ms 이하**면 "좋음", 500ms 초과면 "나쁨"이다. 2024년 3월에 FID를 대체했다.
- **main thread** — 브라우저가 JS 실행, 레이아웃 계산, 화면 그리기를 **한 줄로** 처리하는 작업 통로. 은행 창구 직원이 한 명뿐인 것과 같다. 앞 손님 업무가 길면 뒤 손님(클릭)은 기다린다.
- **long task** — main thread를 50ms 넘게 붙잡는 작업. INP를 망치는 주범.

**원인**
- 클릭 핸들러 안에서 무거운 계산·대량 데이터 정렬을 바로 실행
- 상태 하나 바꿨는데 화면 전체가 다시 렌더링됨
- 수천 개 행을 한 번에 DOM에 그리는 긴 목록
- 광고·분석 같은 서드파티 스크립트가 main thread를 점유

**지시 예문**
- "필터 버튼 누르면 반응이 늦어. 버튼 상태부터 즉시 바꾸고 무거운 필터링은 그다음에 처리해서 INP를 줄여줘."
- "검색 입력할 때마다 목록 전체가 다시 렌더링돼. 입력은 debounce하고 목록은 virtualization 적용해줘."
- "INP가 나빠. Performance 패널 기준으로 long task를 찾아서 쪼개줘."

## Stacking context

**현상** — 모달·드롭다운에 `z-index: 9999`를 줬는데도 헤더나 다른 카드 아래에 깔린다. 숫자를 더 키워도 그대로다.

**용어**
- **stacking context(쌓임 맥락)** — z-index 순서를 따지는 **독립된 층 묶음**. z-index는 같은 묶음 안에서만 비교된다. 묶음 안의 자식이 9999여도, 묶음 자체가 다른 묶음보다 아래면 통째로 아래에 깔린다.
- 비유: 스테이플러로 찍은 종이 묶음. 묶음 안에서 종이 순서는 마음대로 바꿀 수 있지만, 묶음 안의 한 장만 빼서 다른 묶음 위로 올릴 수는 없다.
- **새 묶음을 만드는 속성** (부모에 이게 있으면 의심):
  - `position: relative/absolute` + `z-index` 값 지정
  - `position: fixed/sticky`
  - `transform`, `filter`, `opacity` 1 미만, `will-change`
  - flex/grid 자식에 `z-index` 지정
  - `isolation: isolate` (묶음을 일부러 만들 때 쓰는 속성)

**원인** — 애니메이션용 `transform`, 페이드용 `opacity` 같은 **겉보기와 무관한 속성**이 부모에 걸려 몰래 새 묶음이 생김. 그래서 z-index만 보고는 원인을 못 찾는다.

**지시 예문**
- "모달이 헤더 아래 깔려. z-index 올리지 말고, 부모 중 stacking context를 만드는 요소부터 찾아줘."
- "모달을 portal로 body 바로 아래에 렌더링해서 부모 stacking context에서 빼줘."
- "z-index 값이 여기저기 9999로 난무해. 레이어 순서를 토큰으로 정리해줘 (dropdown < sticky header < modal < toast)."

## Race condition

**현상** — 검색어를 "react" → "redux"로 빠르게 바꿨는데, 화면에 "react" 결과가 남는다. 탭을 빠르게 A → B로 눌렀는데 A 탭 데이터가 B 탭에 뜬다. 가끔만 생기고 재현이 잘 안 된다.

**용어**
- **race condition(경쟁 상태)** — 여러 작업이 동시에 진행될 때, **끝나는 순서**에 따라 결과가 달라지는 버그. 웹에서는 "먼저 보낸 요청이 늦게 도착해 최신 결과를 덮어쓰는" 형태가 가장 흔하다.
- 비유: 배달 앱에서 주소를 A → B로 바꿨는데, 서버에 "A로 변경" 처리가 늦게 끝나 최종 주소가 A로 남는 것. 보낸 순서 ≠ 도착 순서.
- **stale response** — 이미 쓸모없어진(낡은) 요청의 응답. race condition을 막는 핵심은 이걸 버리는 것이다.
- 네트워크가 빠른 개발 환경에선 잘 안 보이고, 느린 모바일 환경에서 터진다. 그래서 "가끔 이상해요"라는 제보로 들어온다.

**원인** — 요청을 보낼 때마다 응답이 오면 **무조건 화면에 반영**하도록 짜서, 응답이 오는 순서를 보장하지 않음.

**해결 방향**
- 새 요청을 보낼 때 이전 요청을 **취소** (`AbortController`)
- 응답이 와도 **최신 요청의 응답인지 확인**하고 아니면 무시
- 데이터 패칭 라이브러리(TanStack Query, SWR)는 이 처리를 기본으로 해준다

**지시 예문**
- "검색어를 빠르게 바꾸면 이전 결과가 남아. race condition 같으니, 새 요청 보낼 때 이전 요청은 AbortController로 취소해줘."
- "탭 전환 시 stale response가 화면을 덮어써. 현재 탭과 다른 응답은 무시하게 해줘."
- "개발자 도구에서 네트워크를 Slow 4G로 두고 race condition 재현되는지 확인해줘."

## Hydration과 hydration mismatch

**현상** — 새로고침 직후 콘솔에 "Hydration failed" / "Text content does not match" 경고가 뜨고, 처음 보인 텍스트가 잠깐 뒤 다른 값으로 바뀐다. 심하면 그 영역이 통째로 다시 그려지며 깜빡인다.

**용어**
- **SSR (Server-Side Rendering)** — 서버가 HTML을 완성해서 보냄. 빨리 보이지만, 이 상태의 HTML은 버튼을 눌러도 반응하지 않는 "그림"이다.
- **CSR (Client-Side Rendering)** — 빈 HTML을 받고 브라우저의 JS가 화면을 만듦.
- **hydration** — SSR로 받은 HTML에 JS가 이벤트·상태를 붙여 **살아 움직이게 만드는 과정**. 정상 동작의 이름이다. 마네킹(HTML)에 사람(JS)이 들어가 움직이는 것.
- **hydration mismatch(hydration error)** — hydration 도중 "서버가 그린 HTML"과 "클라이언트가 같은 코드로 다시 계산한 결과"가 **다른 것**. 버그의 이름은 이쪽이다. 마네킹 자세와 들어간 사람 자세가 안 맞는 셈.

**원인** — 서버와 브라우저에서 **같은 코드가 다른 값을 내는 경우**
- 실행 시점·환경 차이: `new Date()`, `Math.random()`, 서버와 사용자 타임존 차이
- 브라우저에만 있는 값: `window`, `localStorage`, 화면 너비
- 잘못된 HTML 중첩: `<p>` 안에 `<div>`, `<a>` 안에 `<a>` — 브라우저가 HTML을 고쳐 읽어 구조가 달라짐
- 브라우저 확장 프로그램(번역기, 비밀번호 관리자)이 DOM을 먼저 건드림

**지시 예문**
- "날짜 표시에서 hydration mismatch가 나. 서버에선 자리만 그리고, 실제 시간은 마운트 후 클라이언트에서 채워줘."
- "localStorage 값으로 테마를 정하다가 hydration error가 나. 서버와 첫 렌더 결과가 같도록 고쳐줘."
- "hydration error 원인이 잘못된 HTML 중첩인지 먼저 확인해줘 (p 안의 div 등)."

## Virtualization

**현상** — 주문 내역·로그·채팅처럼 행이 수천 개인 목록에 들어가면 첫 화면이 늦게 뜨고, 스크롤이 버벅이며, 필터를 눌러도 반응이 굼뜨다(INP 악화).

**용어**
- **virtualization(가상화, windowing)** — 목록 전체를 DOM에 그리지 않고 **지금 화면에 보이는 행 + 약간의 여유분만** 그리는 기법. 스크롤하면 화면 밖으로 나간 행을 지우고 새로 보일 행을 그린다. 전체 높이만큼의 빈 공간은 유지해서 스크롤바는 정상처럼 보인다.
- 비유: 영화 세트장. 거리 전체를 짓지 않고 카메라에 잡히는 건물 앞면만 세운다. 카메라가 움직이면 그쪽 세트만 새로 세운다.
- **overscan** — 빠르게 스크롤할 때 빈칸이 보이지 않도록 화면 위아래에 미리 그려두는 여유 행 수.
  - 필요한 이유는 행 크기가 아니라 **타이밍 차이**다. 스크롤 자체는 브라우저가 main thread와 별도로 즉시 움직이지만, 새 행을 그리는 건 JS(main thread)라 한 박자 늦다. 그 틈에 아직 안 그린 영역이 드러나 흰 빈칸이 번쩍인다. overscan은 미리 그려둔 행으로 이 틈을 메운다.
  - 트레이드오프: 크게 잡을수록 빈칸은 줄지만 그리는 행이 늘어 virtualization 효과가 줄어든다. 보통 화면 위아래로 몇 행 정도.
  - 세트장 비유로는, 카메라가 빠르게 돌면 세트 짓는 속도가 못 따라가니 옆 건물 몇 채를 미리 세워두는 것.
- 대표 라이브러리: TanStack Virtual, react-window, react-virtuoso

**부작용** — 지시할 때 같이 챙길 것
- 브라우저 찾기(Ctrl+F)로 화면 밖 행을 못 찾는다 — 아직 DOM에 없으니까
- 행 높이가 제각각이면 스크롤 위치가 튀거나 계산이 복잡해진다
- 스크린리더가 전체 개수를 모를 수 있다

**대안** — 수백 개 수준이면 virtualization까지 필요 없을 수 있다. 페이지네이션, 무한 스크롤, CSS `content-visibility: auto`가 더 단순한 선택지다.

**지시 예문**
- "주문 목록이 3천 행이라 스크롤이 버벅여. virtualization 적용해줘. 행 높이는 고정 64px이야."
- "채팅 목록에 virtualization 넣어줘. 메시지 길이에 따라 높이가 달라서 가변 높이를 지원해야 해."
- "목록이 200개 정도인데 virtualization이 꼭 필요한지, content-visibility로 충분한지 먼저 판단해줘."

## FOUC · FOUT · FOIT

**현상** — 페이지가 뜨는 순간 잠깐 이상한 모습이 보였다가 정상으로 바뀐다. 스타일 없는 맨 HTML이 번쩍이거나, 글꼴이 바뀌며 글자가 출렁이거나, 다크 모드인데 흰 화면이 번쩍인다.

**용어** — 전부 "Flash of ~"(~가 번쩍임)의 약자다.
- **FOUC (Flash of Unstyled Content)** — CSS가 적용되기 전의 **맨 HTML**이 잠깐 보임. CSS를 늦게 붙이거나 JS로 스타일을 주입할 때 생긴다.
- **FOUT (Flash of Unstyled Text)** — 웹폰트가 오기 전 **대체 글꼴**로 먼저 보였다가 바뀜. 글자 폭이 달라 줄바꿈이 바뀌면 layout shift(CLS)로 이어진다.
- **FOIT (Flash of Invisible Text)** — 웹폰트가 올 때까지 **글자가 아예 안 보임**. 버튼·제목 자리가 비어 보인다.
- FOUT와 FOIT는 `font-display` 속성으로 고른다. `swap`이면 FOUT(일단 보여줌), `block`이면 FOIT(기다림). 보통 FOUT가 낫다 — 안 보이는 것보다 다른 글꼴이라도 보이는 게 낫기 때문.
- **다크 모드 깜빡임(flash of incorrect theme)** — FOUC의 친척. 저장된 테마를 JS가 늦게 읽어서, 첫 화면이 기본(라이트) 테마로 그려졌다가 다크로 바뀐다.

**원인** — 공통점은 **첫 화면을 그리는 시점에 필요한 정보(CSS·폰트·테마)가 아직 없음**.

**지시 예문**
- "새로고침할 때 다크 모드인데 흰 화면이 번쩍여. 테마를 <head>의 인라인 스크립트에서 첫 paint 전에 적용해줘."
- "웹폰트 로드 때 FOUT로 줄바꿈이 바뀌어. 대체 글꼴 크기를 웹폰트에 맞춰서(size-adjust) layout shift를 없애줘."
- "제목 글자가 1~2초 안 보이다 나타나. FOIT 같으니 font-display: swap으로 바꾸고 폰트를 preload해줘."
