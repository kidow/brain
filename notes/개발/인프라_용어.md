## 서버 · IP · 포트 · 호스팅

**현상**
- 로컬에서 `localhost:3000`으로 잘 보이는데, 같은 와이파이의 휴대폰에서 그 주소를 치면 **안 열린다**.
- 서버를 띄웠는데 `Error: listen EADDRINUSE: address already in use :::3000` 에러가 난다.
- "호스팅 어디로 해요?"라는 질문에 Vercel, AWS, 카페24, 가비아가 다 섞여 나와 **뭐가 뭔지** 모르겠다.

**용어**
- **server(서버)** — 요청을 받아 **응답을 돌려주는 컴퓨터(또는 프로그램)**. 특별한 기계가 아니라, 24시간 켜져 인터넷에 연결된 컴퓨터일 뿐이다. 내 노트북도 `npm run dev`를 하면 잠깐 서버가 된다.
- **IP 주소** — 인터넷에서 컴퓨터를 찾는 **숫자 주소**. `203.0.113.10` 같은 형태(IPv4), 더 긴 IPv6도 있다.
  - **public IP(공인 IP)** — 인터넷 어디서든 찾아올 수 있는 주소.
  - **private IP(사설 IP)** — 집·회사 공유기 안에서만 통하는 주소(`192.168.x.x`).
  - **localhost(127.0.0.1)** — "**나 자신**"을 가리키는 특별한 주소. 휴대폰에서 `localhost`를 치면 **휴대폰 자신**을 찾는다(현상 1의 원인). 같은 와이파이라면 노트북의 사설 IP(`192.168.0.5:3000`)로 접속한다.
- **port(포트)** — 한 컴퓨터 안에서 **어느 프로그램에게 갈지** 정하는 번호. IP가 건물 주소면 포트는 **호수**. `3000`(개발 서버), `5432`(PostgreSQL), `80`(HTTP), `443`(HTTPS). 주소창에 포트를 안 쓰면 80/443이 생략된 것이다.
  - **포트 충돌** — 한 포트는 한 프로그램만 쓴다. 이미 3000번을 다른 프로그램(꺼지지 않은 이전 dev 서버 등)이 쓰고 있으면 현상 2 에러가 난다.
- **hosting(호스팅)** — 내 앱·사이트를 올려둘 **서버를 빌려주는 서비스**. 직접 서버 컴퓨터를 사서 24시간 켜두지 않아도 된다.
  - 종류를 대략 나누면: **플랫폼형**(Vercel, Netlify — 코드만 올리면 알아서 배포), **클라우드**(AWS, GCP, Azure — 서버·DB·저장소 등 부품을 골라 조립), **웹호스팅**(카페24 등 — 전통적인 공간 임대).
  - 비유: 이사 갈 집. 플랫폼형은 **풀옵션 원룸**(바로 입주, 자유도 낮음), 클라우드는 **빈 땅과 건축 자재**(뭐든 지을 수 있지만 직접 지어야 함).
  - 진단 Q1처럼 **도메인을 사는 곳(가비아 등 등록 대행)**과 **호스팅**은 다른 서비스다. 둘을 잇는 게 다음 레슨의 DNS.

**지시 예문**
- "로컬 개발 서버를 같은 와이파이 휴대폰에서 보고 싶어. 0.0.0.0으로 열고 내 맥의 사설 IP 주소를 알려줘."
- "EADDRINUSE 3000 에러가 나. 3000번 포트를 쓰는 프로세스를 찾아서 알려줘."
- "이 Next.js 앱을 어디에 호스팅할지 Vercel과 AWS를 비용·운영 난이도 기준으로 비교해줘."

## 도메인과 DNS

**현상**
- `myshop.com`을 샀는데 주소창에 쳐도 **내 사이트로 연결되지 않는다**(진단 Q1).
- DNS 설정을 바꿨는데 내 컴퓨터에선 새 사이트, 다른 사람은 **옛 사이트**를 본다. 몇 시간 뒤엔 다 바뀌어 있다.
- 도메인 관리처(네임서버)를 Cloudflare로 옮겼더니 **회사 이메일이 안 들어온다**.
- `www.myshop.com`은 되는데 `myshop.com`(www 없이)은 안 된다.

**용어**
- **domain(도메인)** — 사람이 외우기 쉬운 **이름 주소**. 컴퓨터는 IP(숫자)로 찾아가므로, 이름을 숫자로 바꿔주는 장치가 필요하다.
  - **registrar(도메인 등록 대행)** — 도메인을 **사는 곳**(가비아, Namecheap, Cloudflare 등). 1번 레슨 호스팅과 별개.
  - **apex / root domain(루트 도메인)** — `myshop.com` 자체.
  - **subdomain(서브도메인)** — 앞에 붙은 이름. `www.myshop.com`, `api.myshop.com`, `admin.myshop.com`. 각각 다른 서버로 보낼 수 있다.
- **DNS(Domain Name System)** — 도메인 이름을 **IP 주소로 바꿔주는** 인터넷의 전화번호부. "myshop.com이 어디야?" → "203.0.113.10이야".
  - 비유: 휴대폰 연락처. 이름("엄마")을 누르면 번호로 전화가 걸린다. DNS 설정은 **연락처에 이름과 번호를 등록하는 일**.
- **DNS record(레코드)** — 전화번호부의 **한 줄**. 종류별로 역할이 다르다.
  - **A** — 이름 → **IPv4 주소**. `myshop.com → 76.76.21.21`.
  - **AAAA** — 이름 → IPv6 주소.
  - **CNAME** — 이름 → **다른 이름**(별명). `www.myshop.com → cname.vercel-dns.com`. 상대 서비스의 IP가 바뀌어도 따라간다. 보통 **루트 도메인에는 CNAME을 쓸 수 없어서** 루트는 A 레코드, www는 CNAME으로 따로 설정한다(현상 4의 흔한 원인).
  - **MX** — 이 도메인의 **이메일을 받을 서버**.
  - **TXT** — 자유 글자 메모. 도메인 소유 **인증**(구글·Vercel 등이 "이 값을 넣어보세요"), 이메일 위조 방지(SPF 등)에 쓴다.
- **nameserver(네임서버)** — 이 도메인의 **레코드 목록을 실제로 관리하는 곳**. 네임서버를 Cloudflare로 바꾸면 이제 Cloudflare에 적힌 레코드만 유효하다. 옛 관리처에 있던 MX 레코드를 **옮겨 적지 않으면 메일이 끊긴다**(현상 3).
- **TTL · propagation(전파)** — DNS 응답은 전 세계 곳곳에 **임시 저장(캐시)**된다(웹 용어 12번). TTL은 그 저장 유효 시간. 레코드를 바꿔도 옛 캐시가 만료될 때까지 사람마다 옛 주소를 보는 기간이 **전파 지연**이다(현상 2). 보통 몇 분~몇 시간, 길면 하루 이상.

**지시 예문**
- "myshop.com을 Vercel에 연결하려고 해. 루트 도메인과 www에 각각 어떤 DNS record(A·CNAME)를 넣어야 하는지 정리해줘."
- "네임서버를 Cloudflare로 옮기기 전에, 기존 DNS 레코드(특히 MX·TXT)를 전부 목록으로 뽑아줘."
- "DNS 바꿨는데 아직 옛 사이트가 보여. dig로 지금 어떤 IP가 응답되는지, TTL이 얼마인지 확인해줘."
- "api.myshop.com 서브도메인을 백엔드 서버로 연결하는 설정 알려줘."

## HTTPS와 SSL/TLS 인증서

**현상**
- 주소창에 **"주의 요함", "안전하지 않음"** 경고가 뜬다(진단 Q2).
- 잘 되던 사이트가 어느 날 갑자기 **"연결이 비공개로 설정되어 있지 않습니다"** 빨간 경고 화면으로 막힌다.
- HTTPS로 바꿨는데 일부 이미지가 **안 보이고**, 콘솔에 "Mixed Content" 경고가 뜬다.
- `http://`로 들어온 사람은 여전히 경고 화면을 본다.

**용어**
- **HTTP vs HTTPS** — HTTP는 주고받는 내용이 **그대로 보이는** 통신, HTTPS는 **암호화된** 통신(S = Secure). HTTP에선 같은 와이파이의 누군가가 비밀번호·쿠키를 엿볼 수 있다. 요즘 브라우저는 HTTP 사이트에 경고를 띄운다.
  - 비유: HTTP는 **엽서**(배달부가 다 읽을 수 있음), HTTPS는 **봉인된 편지**.
- **SSL / TLS** — HTTPS의 암호화를 해주는 **규약**. SSL은 옛 이름이고 지금 쓰는 건 TLS인데, 관습적으로 "SSL 인증서"라고 부른다. 둘을 같은 말로 봐도 실무에선 통한다.
- **SSL/TLS 인증서(certificate)** — "이 도메인의 진짜 주인이 맞다"를 증명하는 **디지털 신분증**. 이게 있어야 HTTPS가 켜진다. 진단 Q2에서 "없는 것"의 정확한 이름.
  - **CA(Certificate Authority, 인증 기관)** — 인증서를 **발급해 주는 신뢰 기관**. 브라우저는 믿을 만한 CA 목록을 내장하고 있다.
  - **Let's Encrypt** — 인증서를 **무료로 자동 발급**하는 대표 CA. Vercel·Netlify·Cloudflare는 도메인을 연결하면 이걸로 **알아서 발급·갱신**해 준다.
- **인증서 만료(expiration)** — 인증서엔 **유효기간**이 있다(Let's Encrypt는 몇 달 단위로 짧다). 갱신을 놓치면 어느 날 갑자기 경고 화면으로 막힌다(현상 2). 직접 서버를 운영할 땐 **자동 갱신**을 반드시 설정한다.
- **mixed content(혼합 콘텐츠)** — HTTPS 페이지 안에서 이미지·스크립트를 `http://` 주소로 불러오는 것. 브라우저가 막거나 경고한다(현상 3). 모든 리소스 주소를 `https://`로 바꾼다.
- **HTTP → HTTPS redirect(리다이렉트)** — `http://`로 들어온 요청을 `https://`로 **자동으로 옮겨주는** 설정(웹 용어 28번 301). 현상 4의 해결.
  - **HSTS** — 브라우저에게 "이 사이트는 앞으로 **무조건 HTTPS로만** 접속해"라고 기억시키는 설정. 한 단계 더 강한 방어.

**지시 예문**
- "사이트에 '안전하지 않음' 경고가 떠. 도메인에 SSL 인증서가 발급됐는지, http → https redirect가 설정됐는지 확인해줘."
- "콘솔에 Mixed Content 경고가 나와. http://로 불러오는 리소스를 전부 찾아서 https로 바꿔줘."
- "직접 운영하는 서버에 Let's Encrypt 인증서를 붙이고 자동 갱신까지 설정해줘."
- "인증서 만료일을 확인하고, 만료 2주 전에 알림이 오게 해줘."

## 실행 방식: VM · container · serverless

**현상**
- "내 컴퓨터에선 되는데 서버에선 안 돼요." Node 버전·라이브러리가 서버마다 다르다(진단 Q3).
- 서버를 한 대 빌려 24시간 켜뒀더니 **방문자가 거의 없는데도 매달 요금**이 나간다.
- 서버리스 함수에서 임시로 저장한 파일이 **다음 요청에선 사라져** 있다. 긴 작업은 중간에 **시간 초과**로 끊긴다.

**용어** — 내 코드를 **어떤 형태의 서버 위에서 돌릴지**의 선택지. 아래로 갈수록 내가 관리할 게 적고, 대신 제약이 생긴다.
- **VM(Virtual Machine, 가상 서버)** — 큰 물리 서버를 쪼개 만든 **가상의 컴퓨터 한 대**. OS부터 직접 설치·관리한다. 자유도 최고, 관리 부담 최고. 꺼지지 않고 **켜져 있는 시간만큼 과금**(현상 2).
  - 비유: **집 한 채 임대**. 가구·전기·보안 다 내가 챙긴다.
- **container(컨테이너)** — 앱과 실행에 필요한 것(언어 버전·라이브러리·설정)을 **통째로 포장한 상자**. OS 전체를 넣는 VM보다 가볍고, **어디서 실행해도 똑같이 동작**한다(현상 1 해결). 진단 Q3의 개념 이름.
  - 비유: 해운 **컨테이너**. 규격이 같으니 어느 배·트럭·항구에서도 그대로 싣고 내린다. 안에 뭐가 들었는지 배는 신경 쓰지 않는다.
  - **Docker** — 컨테이너를 만들고 돌리는 대표 도구.
  - **Dockerfile** — 상자를 **어떻게 쌀지 적은 레시피**("Node 20 깔고, 의존성 설치하고, 이 명령으로 실행").
  - **image(이미지)** — 레시피대로 싸 놓은 **완성된 상자 원본**(실행 전).
  - **container** — 이미지를 **실제로 실행 중인** 것. 한 이미지로 여러 컨테이너를 띄울 수 있다(붕어빵 틀 = 이미지, 붕어빵 = 컨테이너).
  - **registry(레지스트리)** — 이미지를 올려두는 **저장소**(Docker Hub 등). 서버는 여기서 이미지를 받아 실행한다.
- **serverless(서버리스)** — 서버를 **내가 전혀 관리하지 않고**, 요청이 올 때만 **함수가 잠깐 실행**되는 방식(Vercel Functions, AWS Lambda 등). 서버가 없는 게 아니라 **안 보이는** 것.
  - **사용한 만큼만 과금** — 요청이 없으면 거의 0원(현상 2 해결).
  - **stateless(상태 없음)** — 실행이 끝나면 그 환경이 사라질 수 있어서, 디스크·메모리에 둔 것은 **다음 요청에 남아 있다는 보장이 없다**(현상 3 전반). 파일은 object storage, 데이터는 DB에 둔다.
  - **실행 시간 제한(timeout)** — 한 번 실행에 최대 시간이 있다. 긴 작업은 끊긴다(현상 3 후반, 웹 용어 28번 504). 긴 작업은 큐·백그라운드 작업으로 뺀다.
  - **cold start**(데이터베이스 용어 13번) — 한동안 안 쓰다 처음 깨어날 때 느림.
  - 비유: **택시**. 차를 소유·정비하지 않고 탈 때만 요금. 대신 트렁크에 짐을 두고 내리면 다음 택시엔 없다.
- 고르는 기준: 대부분의 웹앱(Next.js 등) → **serverless 플랫폼**이 쉽다. 오래 도는 작업·웹소켓 서버(웹 용어 24번)·특수 환경 → **container**. OS 수준 제어가 필요 → **VM**.

**지시 예문**
- "이 앱을 Dockerfile로 컨테이너화해줘. Node 20, 프로덕션 빌드, 이미지 크기 작게."
- "서버리스 함수에서 /tmp에 파일을 저장하고 다음 요청에서 읽고 있어. stateless라 사라질 수 있으니 object storage에 저장하게 바꿔줘."
- "PDF 생성이 서버리스 timeout에 걸려. 요청은 바로 응답하고 생성은 백그라운드 작업으로 빼줘."
- "WebSocket 서버가 필요한데 서버리스로 가능한지, 컨테이너로 따로 띄워야 하는지 비교해줘."

## Object storage: bucket · public/private · presigned URL

**현상**
- 사용자 프로필 사진을 서버 디스크에 저장했더니, 재배포하거나 서버를 늘리면 **파일이 사라지거나 서버마다 다르다**(진단 Q5, 4번 레슨 stateless).
- 동영상 같은 큰 파일을 서버리스 함수로 받아서 저장하려니 **`413 Payload Too Large`**나 시간 초과가 난다.
- 비공개여야 할 계약서 파일 주소를 누가 알게 되면 **아무나 열어볼 수 있다**.

**용어**
- **object storage(오브젝트 스토리지)** — 이미지·영상·PDF 같은 **파일을 전문으로 보관**하는 별도 저장소. 서버와 분리돼 있어 서버가 몇 대든, 다시 배포되든 파일은 그대로다. 용량이 사실상 무제한이고 싸다. 진단 Q5의 답.
  - 대표 서비스: **AWS S3**(사실상 표준이라 다른 서비스도 "S3 호환"을 내세움), Cloudflare R2, Supabase Storage, Vercel Blob.
  - 비유: **물류 창고**. 가게(서버)에 물건을 쌓아두지 않고 창고에 맡긴 뒤 **보관 번호**로 꺼낸다. 가게가 이사해도 창고 물건은 그대로.
- **bucket(버킷)** — 파일을 담는 **최상위 통**. 용도별로 나눈다(`avatars`, `documents`).
- **object · key** — 저장된 파일 하나가 object, 그 **이름(경로처럼 생긴 문자열)**이 key. `avatars/user-123/profile.jpg`. 폴더처럼 보이지만 실제로는 이름에 `/`가 들어간 것.
- **DB에는 파일 대신 key(또는 URL)만** 저장한다. 파일 자체를 DB에 넣으면 DB가 무거워진다(DB 용어 15번 데이터 타입 선택과 같은 맥락).
- **public vs private** — public 버킷은 주소만 알면 **누구나** 열 수 있다(상품 이미지에 적합). private 버킷은 **권한 확인 후에만** 접근(계약서·신분증·영수증). 민감한 파일을 public에 두면 현상 3이 된다.
- **presigned URL(서명된 임시 URL)** — private 파일에 **잠깐만 유효한 출입증 붙은 주소**를 만들어 주는 것. "10분 동안만 이 파일을 다운로드할 수 있는 링크". 권한 검사는 서버가 하고, 링크를 발급해 준다.
  - 비유: 호텔 **일회용 카드키**. 체크아웃 시간이 지나면 같은 카드로 문이 안 열린다.
- **direct upload(직접 업로드)** — 큰 파일을 **서버를 거치지 않고 브라우저에서 스토리지로 바로** 올리는 방식. 서버는 업로드용 presigned URL만 발급하고, 파일은 직접 간다. 서버리스의 요청 크기·시간 제한을 피한다(현상 2 해결).
- **CDN 앞단 연결** — 자주 보는 이미지는 스토리지 앞에 CDN(웹 용어 12번)을 붙여 빠르게, 싸게 내려준다.

**지시 예문**
- "프로필 사진을 서버 디스크 대신 S3(또는 Supabase Storage)에 저장하고, DB에는 key만 저장하게 바꿔줘."
- "동영상 업로드가 413 에러로 실패해. 서버는 presigned URL만 발급하고 브라우저에서 스토리지로 direct upload 하게 바꿔줘."
- "계약서 파일은 private 버킷에 두고, 본인 확인 후 10분짜리 presigned URL로만 다운로드되게 해줘."
- "상품 이미지 버킷은 public으로 두고 앞에 CDN을 붙여줘."

## 확장: scale up/out · load balancer · health check · autoscaling

**현상**
- 이벤트 날 접속자가 몰리자 서버 한 대가 **버티지 못하고 죽었다**. 그날 서비스 전체가 멈췄다.
- 서버를 3대로 늘렸더니, 로그인했다가 새로고침하면 **가끔 로그아웃**된다.
- 밤엔 접속자가 거의 없는데 서버 10대가 **계속 켜져서** 요금만 나간다.

**용어**
- **scale up(수직 확장)** — 서버 한 대를 **더 좋은 사양**(CPU·메모리)으로 바꾸는 것. 간단하지만 한계가 있고, 그 한 대가 죽으면 끝.
- **scale out(수평 확장)** — 비슷한 서버를 **여러 대로 늘리는** 것. 이론상 계속 늘릴 수 있고 한 대가 죽어도 나머지가 버틴다.
  - 비유: 식당이 붐빌 때 **요리사 한 명을 더 빠른 사람으로 교체**(scale up) vs **요리사를 여러 명 고용**(scale out).
- **SPOF(Single Point Of Failure, 단일 장애점)** — **그것 하나만 죽으면 전체가 멈추는** 지점. 서버 한 대 운영이면 그 서버가 SPOF(현상 1). 여러 대로 나눠 없애는 것을 **이중화(redundancy)**라 한다.
- **load balancer(로드밸런서)** — 여러 서버 **앞단에서 요청을 골고루 나눠주는** 장치. 진단 Q4의 답. 사용자는 로드밸런서 주소 하나만 알면 되고, 뒤에 서버가 몇 대인지 모른다.
  - 비유: 은행 **번호표 기계와 안내 직원**. 손님을 비어 있는 창구로 보내고, 쉬는 창구로는 안 보낸다.
- **health check(헬스 체크)** — 로드밸런서가 각 서버에 주기적으로 "**살아 있어?**"를 물어보는 것(보통 `/health` 같은 주소). 응답이 없는 서버로는 요청을 안 보낸다. 진단 Q4의 "한 대가 죽으면 그쪽으로 안 보냄"이 이것.
- **stateless 서버** — 4번 레슨처럼, scale out을 하려면 **어느 서버가 요청을 받아도 똑같이** 처리해야 한다. 로그인 세션을 서버 메모리에 두면, 다음 요청이 다른 서버로 갈 때 "모르는 사람"이 된다(현상 2). 세션은 **Redis·DB**(DB 용어 19번)나 토큰(웹 용어 23번)으로 공유 저장소에 둔다.
  - **sticky session** — 같은 사용자를 **항상 같은 서버로** 보내는 로드밸런서 설정. 임시방편은 되지만 그 서버가 죽으면 세션이 날아가 근본 해결은 아니다.
- **autoscaling(오토스케일링)** — 부하(CPU 사용률·요청 수)에 따라 서버 수를 **자동으로 늘리고 줄이는** 것. **최소·최대 대수**를 정해 둔다. 밤에 줄여 비용 절감(현상 3 해결), 이벤트 때 늘려 버틴다. 서버리스(4번 레슨)는 이게 기본으로 내장된 형태.

**지시 예문**
- "서버를 2대 이상으로 scale out하고 앞에 load balancer를 두려고 해. 서버를 stateless하게 만들려면 뭘 바꿔야 하는지 먼저 점검해줘."
- "서버 늘린 뒤 가끔 로그아웃돼. 세션을 서버 메모리 대신 Redis에 저장하게 바꿔줘."
- "로드밸런서용 /health 엔드포인트 만들어줘. DB 연결까지 확인해서 실패하면 503을 돌려주게."
- "CPU 70% 기준으로 최소 2대, 최대 10대 autoscaling 설정해줘."

## 비동기 작업: queue · worker · retry · cron

**현상**
- 회원가입 버튼을 누르면 환영 이메일 발송·썸네일 생성까지 다 끝날 때까지 **5초씩 기다린다**.
- 이메일 발송 서비스가 잠깐 장애였을 뿐인데 **회원가입 자체가 실패**했다.
- 동영상 변환이 서버리스 timeout(4번 레슨)에 걸려 **중간에 끊긴다**.
- 매일 아침 9시 정산·만료 쿠폰 정리를 **누군가 수동으로** 돌리고 있다.

**용어**
- **동기 vs 비동기 처리** — **동기**는 작업이 끝날 때까지 사용자가 **기다리는** 방식, **비동기**는 "접수됐어요"라고 **먼저 응답하고 뒤에서 처리**하는 방식. 사용자가 결과를 당장 볼 필요 없는 일(이메일, 이미지 변환, 통계, 외부 연동)은 비동기로 뺀다(현상 1 해결).
- **background job(백그라운드 작업)** — 요청 흐름 밖에서 **뒤에서 도는 작업**.
- **queue(큐, 작업 대기열)** — 해야 할 작업을 **줄 세워 쌓아두는** 곳. 요청 처리 코드는 "이메일 보내기" 작업을 큐에 넣기만 하고 바로 응답한다.
  - **producer** — 작업을 큐에 **넣는** 쪽(우리 API).
  - **worker / consumer** — 큐에서 작업을 **꺼내 실제로 처리하는** 쪽. 일이 밀리면 worker를 늘린다(6번 레슨 scale out).
  - 비유: 식당 **주문표 꽂이**. 홀 직원(producer)은 주문표를 꽂고 바로 다음 손님을 받는다. 주방(worker)이 순서대로 꺼내 요리한다. 주방이 잠깐 바빠도 주문은 사라지지 않고 쌓여 있다.
- **retry(재시도)** — 작업이 실패하면 **잠시 뒤 다시 시도**. 외부 서비스의 일시 장애를 흡수한다(현상 2 해결: 가입은 성공시키고, 이메일 작업만 나중에 재시도).
  - **exponential backoff(지수 백오프)** — 재시도 간격을 **1초 → 2초 → 4초 → 8초**처럼 점점 늘리는 것. 장애 난 서비스를 계속 두드리지 않는다.
  - 재시도된다는 건 **같은 작업이 두 번 실행될 수 있다**는 뜻이라, 작업을 **멱등하게**(웹 용어 27번) 만든다. 이메일이 두 번 가지 않도록.
- **dead letter queue(DLQ, 실패 작업 보관함)** — 여러 번 재시도해도 실패한 작업을 **따로 모아두는** 큐. 버리지 않고 나중에 사람이 확인한다.
- **cron(크론) / scheduled job(예약 작업)** — **정해진 시각마다 자동 실행**되는 작업. "매일 9시", "매시 정각"(현상 4 해결).
  - **cron 표현식** — 시간 규칙을 쓰는 형식. `0 9 * * *` = 매일 9시 0분(분·시·일·월·요일 순). 서버 시간대가 **UTC**인 경우가 많아 한국 9시는 `0 0 * * *`가 될 수 있다(웹 용어 26번).
- 서비스 예: AWS SQS, Redis 기반 큐, Vercel Cron, 워크플로 도구 등. 긴 작업(현상 3)은 큐 + 별도 worker(컨테이너)로 서버리스 시간 제한을 피한다.

**지시 예문**
- "회원가입 응답이 느려. 환영 이메일과 썸네일 생성을 queue에 넣고 worker가 비동기로 처리하게 바꿔줘."
- "이메일 작업이 실패하면 exponential backoff로 5번까지 retry하고, 그래도 실패하면 DLQ에 남겨줘. 두 번 발송되지 않게 멱등하게."
- "만료 쿠폰 정리를 매일 한국 시간 새벽 3시에 도는 cron으로 만들어줘. 서버가 UTC인지 확인하고 표현식 맞춰줘."
