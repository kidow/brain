## Primary key와 foreign key

**현상**
- 회원을 삭제했더니, 그 회원이 쓴 글이 **존재하지 않는 회원 ID**를 가리킨 채 남는다. 글 목록에서 작성자를 불러오다 에러가 나거나 "알 수 없음"으로 뜬다.
- 같은 사람이 두 번 등록됐는데 어느 행이 진짜인지 구분할 방법이 없다.

**용어**
- **table · row · column** — 표 하나(table), 그 안의 한 줄 = 데이터 하나(row, 행), 세로 칸 = 속성(column, 열). 엑셀 시트·행·열과 같다.
- **primary key(PK, 기본 키)** — 각 row를 **유일하게 가리키는 값**. 중복·빈 값 불가. 보통 `id` 컬럼.
  - 비유: 주민등록번호. 이름이 같은 사람은 있어도 번호가 같은 사람은 없다.
- **foreign key(FK, 외래 키)** — 다른 테이블의 PK를 **가리키는 컬럼**. `posts.author_id` → `users.id`. 두 테이블 사이의 **관계**를 만든다.
- **FK 제약(foreign key constraint)** — "가리키는 대상이 **실제로 존재해야 한다**"를 DB가 강제하는 규칙. 없는 회원 ID로 글을 쓰려 하거나, 글이 남아 있는 회원을 지우려 하면 DB가 막는다. FK 컬럼만 있고 **제약을 안 걸면** 위 현상(주인 없는 글)이 생긴다.
- **orphan(고아) 데이터** — 가리키던 부모가 사라져 **홀로 남은 row**. 위 현상의 이름.
- **ON DELETE 옵션** — 부모(회원)를 지울 때 자식(글)을 어떻게 할지 정하는 FK 설정.
  - **CASCADE** — 자식도 **함께 삭제**. "회원 탈퇴 시 그 사람 글도 삭제".
  - **SET NULL** — 자식은 남기고 작성자 칸만 **비움**. "탈퇴해도 글은 남기고 '탈퇴한 사용자'로 표시".
  - **RESTRICT / NO ACTION** — 자식이 있으면 **부모 삭제를 거부**. 기본값인 경우가 많다.
  - 비유: 아파트 세대주가 이사 갈 때 — 가족도 다 같이 이사(CASCADE), 가족은 남고 세대주 칸만 공란(SET NULL), 가족이 남아 있으면 전출 불가(RESTRICT).

**지시 예문**
- "posts.author_id에 users.id를 가리키는 foreign key 제약을 걸어줘. 회원 탈퇴 시 글은 남기고 작성자만 비우게 ON DELETE SET NULL로."
- "댓글은 글이 삭제되면 같이 지워져야 해. comments.post_id FK를 ON DELETE CASCADE로 해줘."
- "기존 데이터에 orphan row가 있는지 먼저 찾아주고, 정리한 뒤에 FK 제약을 추가해줘."
