## 사회공학과 피싱: phishing · spear phishing · smishing · vishing · BEC · 딥페이크

**상황**
- "계정이 정지될 예정입니다. 본인 확인하세요"라는 **택배사·은행 사칭 문자**의 링크를 눌렀더니 진짜와 똑같은 로그인 화면이 나왔다(진단 Q1).
- 대표 이름으로 "**급하게 거래처에 송금해야 하니 이 계좌로 300만 원 보내 주세요. 회의 중이라 전화는 어려워요**"라는 메일·메신저가 왔다.
- 회사 대표의 **목소리**로 전화가 와서 "지금 바로 처리해"라고 했는데, 나중에 보니 **AI로 만든 가짜 목소리**였다.
- npm 관리자가 "2FA(Two-Factor Authentication) 갱신이 필요하다"는 npm 사칭 메일에 속아 계정을 빼앗겼다(웹·앱 보안 7번 레슨 2025년 npm 사건).

**용어**
- **social engineering(사회공학)** — 기술의 빈틈이 아니라 **사람의 심리**(신뢰, 다급함, 두려움, 권위에 대한 복종, 호기심)를 이용해 정보를 빼내거나 행동을 시키는 공격. 아무리 시스템이 튼튼해도 **사람이 문을 열어 주면** 끝이다. 실제 사고의 출발점으로 가장 흔한 경로 중 하나.
- **phishing(피싱)** — 믿을 만한 곳을 **사칭**해서 비밀번호·카드번호·인증 코드를 입력하게 하거나 악성 파일을 열게 하는 것(진단 Q1). "fishing(낚시)"을 비튼 말.
  - **spear phishing(스피어 피싱, 표적 피싱)** — 아무에게나 뿌리지 않고 **특정 사람·회사를 조사해서** 맞춤으로 만든 피싱. 실제 거래처 이름·진행 중인 프로젝트를 언급해 훨씬 그럴듯하다. 작살(spear)로 한 마리를 노린다는 뜻.
  - **smishing(스미싱)** — **문자(SMS(Short Message Service))**로 오는 피싱. 택배·은행·과태료 사칭이 단골.
  - **vishing(비싱)** — **음성 전화(voice)**로 하는 피싱. 한국의 "보이스피싱"이 이것.
  - 비유: 낚시꾼이 **미끼**를 던지는 것. 그물처럼 넓게 던지면 일반 피싱, 특정 물고기의 습성을 연구해 그 물고기만 노리면 스피어 피싱.
- **pretexting(프리텍스팅, 구실 만들기)** — "IT팀인데 점검 중이라 비밀번호 확인 필요해요"처럼 **그럴듯한 상황·역할**을 꾸며 접근하는 수법. 많은 사회공학 공격의 뼈대.
- **BEC(Business Email Compromise, 비즈니스 이메일 사기)** — 대표·임원·거래처를 사칭(또는 실제 계정 탈취)해 **송금·계좌 변경**을 요구하는 사기(상황 2). "CEO 사기"라고도 한다. 피해 금액이 큰 사이버 범죄 유형 중 하나.
- **deepfake(딥페이크)** — AI로 만든 **가짜 목소리·얼굴·영상**(상황 3). 몇 초 분량의 목소리 샘플로도 흉내 낼 수 있어, "목소리가 맞으니 본인"이라는 확인 방식이 더는 안전하지 않다. 영상 회의에 등장한 가짜 임원들에게 속아 큰돈을 송금한 해외 기업 사례도 보도됐다.
- **흔한 심리 장치** — 다급함("오늘 안 하면 정지"), 권위("대표 지시"), 비밀 유지("아무에게도 말하지 마"), 두려움("법적 조치"), 이득("당첨"). 이 신호가 보이면 **멈춘다**.
- **방어**
  - **다른 경로로 확인(out-of-band verification)** — 메일로 온 송금 요청은 **이미 알고 있는 번호로 직접 전화**해 확인. 문자의 링크 대신 **직접 앱·주소를 입력**해 접속. 상황 2·3을 막는 가장 효과적인 습관.
  - **확인 절차를 규칙으로** — "계좌 변경·송금은 두 사람 확인", "가족·팀 간 암호 질문". 사람의 판단이 아니라 **절차**가 막게 한다.
  - **피싱에 강한 로그인** — 가짜 사이트에 비밀번호를 넣어도 소용없게 만드는 **passkey(패스키)·보안 키**(다음 레슨). 상황 4 같은 계정 탈취를 크게 줄인다.
  - **링크 주소 확인** — 표시된 글자가 아니라 **실제 도메인**을 본다(`npmjs.help` ≠ `npmjs.com`, 인프라 용어 2번).

**지시 예문**
- "우리 팀 송금·계좌 변경 절차를 만들어줘: 메일·메신저 요청만으로는 처리 금지, 등록된 번호로 전화 확인, 금액 기준 이상은 두 사람 승인."
- "고객에게 보낼 피싱 주의 안내문을 써줘: 우리는 문자로 로그인 링크를 보내지 않는다는 사실, 공식 도메인 목록, 의심될 때 신고 방법."
- "우리 서비스를 사칭하는 비슷한 도메인(오타·하이픈·다른 최상위 도메인)이 등록돼 있는지 찾아줘."

## 계정 지키기: password manager · MFA 종류 · MFA fatigue · SIM swap · passkey

**상황**
- 여러 사이트에 **같은 비밀번호**를 쓰다가 한 곳이 유출되자, GitHub·클라우드 계정까지 줄줄이 털렸다(웹·앱 보안 3번 레슨 credential stuffing).
- 문자 인증으로 2단계 인증을 켜 뒀는데, 공격자가 통신사에 **내 번호로 유심을 재발급**받아 인증 문자를 가로챘다.
- 새벽에 "로그인 승인하시겠습니까?" **푸시 알림이 수십 번** 와서, 귀찮아서 승인을 눌러 버렸다.
- 비밀번호와 인증 앱 코드를 모두 입력했는데도, 그게 **가짜 로그인 페이지**였어서 계정을 뺏겼다(1번 레슨 피싱).

**용어**
- **password manager(비밀번호 관리자)** — 사이트마다 **길고 무작위인 다른 비밀번호**를 만들어 저장·자동 입력해 주는 도구. 사람이 외울 필요가 없으니 **재사용**(상황 1)을 끊는다. 또 등록된 진짜 도메인에서만 자동 입력되어, 가짜 사이트에선 입력이 안 되는 것이 **피싱 경보** 역할도 한다.
- **MFA(Multi-Factor Authentication, 다단계 인증) / 2FA(Two-Factor Authentication, 2단계 인증)** — 비밀번호(**아는 것**)에 더해 **가진 것**(휴대폰·보안 키)이나 **나 자신**(지문·얼굴)을 함께 확인(인프라 용어 11번). 방식마다 강도가 다르다(약한 것 → 강한 것):
  - **SMS(Short Message Service) 인증 문자** — 가장 약하다. **SIM swap(유심 탈취)**(상황 2)·문자 가로채기에 취약. 없는 것보단 낫지만 중요한 계정엔 피한다.
  - **TOTP(Time-based One-Time Password, 시간 기반 일회용 비밀번호)** — 인증 앱(Google Authenticator 등)이 30초마다 바꾸는 6자리 코드. 문자보다 안전. 그러나 가짜 사이트에 **코드까지 입력하면** 공격자가 즉시 써 버릴 수 있다(상황 4).
  - **push 승인** — 앱에 "로그인하시겠습니까?" 알림. 편하지만 아래 MFA fatigue에 약하다. 화면에 뜬 **숫자를 맞춰 입력**하는 방식(number matching)이 이를 보완한다.
  - **hardware security key(하드웨어 보안 키) · passkey(패스키)** — 가장 강하다. **FIDO2(Fast IDentity Online 2)·WebAuthn(Web Authentication)** 표준 기반으로, 인증이 **진짜 도메인에 묶여** 있어서 가짜 사이트에선 **작동 자체를 안 한다**. 그래서 "**피싱 저항(phishing-resistant)**" 인증이라 부른다(상황 4 해결).
- **MFA fatigue / push bombing(인증 피로 공격)** — 비밀번호를 알아낸 공격자가 **승인 요청을 수십 번 반복**해 사용자가 지쳐서(또는 실수로) 승인하게 만드는 것(상황 3). 2022년 우버(Uber) 침해 사고의 출발점으로 널리 알려졌다. **내가 시도하지 않은 승인 요청은 절대 승인하지 않고**, 오히려 **비밀번호가 샜다는 신호**로 보고 즉시 바꾼다.
- **SIM swap(심 스와핑, 유심 탈취)** — 공격자가 피해자를 사칭해 통신사에서 **유심을 재발급**받아 전화번호를 가로채는 것(상황 2). 문자 인증·전화 인증을 모두 무력화한다. 통신사의 **유심 보호·번호 이동 잠금** 서비스를 켜 두고, 중요한 계정은 문자 인증에 의존하지 않는다.
- **passkey(패스키)** — 비밀번호 대신 **기기(폰·노트북)에 저장된 암호 열쇠 + 지문·얼굴·PIN(Personal Identification Number)**으로 로그인하는 방식. 외울 것도, 유출될 비밀번호도 없고, 피싱 사이트에선 작동하지 않는다. 지원하는 서비스(GitHub, Google, Apple 등)부터 켜 둔다.
  - 비유: 비밀번호·인증 코드는 **말로 전하는 암호**라 엿듣거나 속여서 받아 낼 수 있다. 패스키는 **진짜 문에만 맞는 열쇠** — 가짜 문(피싱 사이트)엔 아예 꽂히지 않는다.
- **account recovery(계정 복구)가 약한 고리** — 아무리 강한 인증을 걸어도 "비밀번호 찾기"가 **문자 하나로** 뚫리면 소용없다. **recovery code(복구 코드)**는 비밀번호 관리자나 오프라인에 안전하게 보관하고, 복구 수단(이메일·전화)도 함께 강화한다.
- **우선순위** — 모든 계정을 똑같이 지킬 수 없다면 **이메일**(다른 계정 복구의 열쇠), **GitHub·클라우드·도메인 등록 업체**(서비스 전체의 열쇠), **결제·은행**부터. 바이브코더에겐 **GitHub과 클라우드 콘솔**이 곧 회사 전체다.

**지시 예문**
- "내가 쓰는 핵심 계정(이메일, GitHub, Vercel, Supabase, AWS, 도메인 등록 업체, npm)의 2단계 인증 설정 방법을 정리해줘. 각각 passkey·보안 키 지원 여부와 문자 인증을 끄는 방법까지."
- "우리 서비스 로그인에 passkey(WebAuthn) 옵션을 추가하는 구현 계획을 세워줘. 기존 비밀번호 로그인과 함께 쓰는 방식으로."
- "우리 서비스의 비밀번호 재설정·계정 복구 흐름이 문자 하나로 뚫리지 않는지 점검해줘. 복구 코드 발급과 보관 안내도 추가하고."
